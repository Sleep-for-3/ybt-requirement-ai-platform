# 07｜真实项目源码学习路线

原则：按一条用户请求纵向阅读，不要先从所有 model 或所有 API 横向扫一遍。每一步都先看测试，因为测试告诉你系统承诺了什么。

项目根目录：`ybt-requirement-ai-platform/`

## 阅读方法

对每条链记录四件事：

```text
入口：谁触发？
状态：读写哪些模型？
边界：有哪些权限、校验、失败和降级？
证据：哪个测试证明它？
```

每读完一条链，画一张时序图并写一段两分钟面试回答。

## 第一步：LLM 调用链

### 阅读顺序

1. `backend/tests/test_llm_gateway.py`
2. `backend/app/services/llm/base.py`
3. `backend/app/services/llm/mock.py`
4. `backend/app/services/llm/openai_compatible.py`
5. `backend/app/services/llm/factory.py`
6. `backend/app/services/llm/prompt_runtime.py`
7. `backend/app/core/settings.py`
8. 在 `backend/app/models/entities.py` 中定位 `ModelProfile`、`PromptTemplateVersion`、`ModelCallLog`

### 理解的思想

- Gateway/Adapter：业务只依赖 `LLMService`，供应商实现可替换。
- Mock 是架构能力，不只是临时假数据：CI 可复现、无需密钥。
- Prompt 与 ModelProfile 是运行时配置，不散落在 API 路由。
- `prepare_model_input` 根据本地/外部模型和敏感等级决定阻断或脱敏。
- 调用日志通过 input hash、Prompt 版本和 retrieval log 建立可追溯关系。

### 要主动发现的缺口

- `response_format=json_object` 不是严格 JSON Schema。
- `temperature` 固定在 provider，`top_p` 未显式配置。
- `token_usage_json` 当前为空，成本不可量化。
- provider 异常缺少细分类、重试/熔断和统一错误模型。
- `record_model_call` 的计时默认写法可能无法记录未传 `started` 的真实耗时。

### 你应做的改造

定义 `LLMRequest`/`LLMResponse`，包含模型参数、Schema、usage、finish reason、provider request id；让输出进入 Pydantic 校验，并补测试。

### 面试表达

> 我没有让业务代码直接依赖 OpenAI SDK，而是抽象了异步 LLMService 和运行时模型配置。Prompt、模型和调用日志可追踪，Mock provider 支持 CI。敏感内容在外发前按分类阻断或脱敏。当前下一步是把 JSON mode 升级为严格 Schema、补 token/cost 和统一重试熔断。

## 第二步：RAG 链路

### 阅读顺序

1. `backend/tests/test_knowledge_rag.py`
2. `backend/app/services/knowledge_ingestion/parsers.py`
3. `backend/app/services/knowledge_ingestion/normalizer.py`
4. `backend/app/services/knowledge_ingestion/ingestion_service.py`
5. `backend/app/services/retrieval/keyword_index.py`
6. `backend/app/services/embeddings/base.py`、`factory.py`
7. `backend/app/services/vector/base.py`、`mock.py`、`milvus.py`
8. `backend/app/services/retrieval/hybrid_retriever.py`
9. `backend/app/services/rag/grounded_answer_service.py`
10. `backend/app/services/rag/citation_validator.py`
11. `backend/app/api/knowledge_rag.py`

### 理解的思想

- 解析后的核心不是“文本”，而是带出处、范围、版本和敏感等级的 `KnowledgeUnit`。
- PostgreSQL 是事实/权限主库，向量库是可重建索引。
- 混合检索先处理可见性，再合并关键词、向量和业务规则。
- 无证据固定拒答；citation 在保存/返回前查库校验。
- RetrievalLog 是评测和线上排障的桥。

### 要主动发现的缺口

- 当前关键词索引不是标准 BM25。
- 当前 `rerank_score` 是加权规则，不是真正 cross-encoder reranker。
- 分数线性融合的标度可能不稳定。
- citation 主要验证 ID 和可见性，尚未逐 claim 验证支持关系。
- query rewriting、时效/权威冲突处理仍可深化。

### 你应做的改造

在不改生成层的前提下实现 RRF 融合，对 50 条黄金集比较 Recall@5/10 和 MRR；之后再加 reranker，证明增益是否值得延迟。

### 面试表达

> 我的 RAG 不是简单向量搜索。先按项目、机构、场景和有效状态做结构化过滤，再用关键词处理字段代码、用向量处理同义表达，最后按业务权威性排序。生成层只接收 Top-K 可见证据，无证据拒答，citation 还要回库验证。检索、生成和系统指标分层评测。

## 第三步：业务口径与技术溯源生成

### 阅读顺序

1. `backend/tests/test_scenario_traceability.py`
2. `backend/tests/test_double_layer_mapping.py`
3. `backend/app/services/mapping/scenario_draft_generator.py`
4. `backend/app/services/mapping/source_to_mart_generator.py`
5. `backend/app/services/mapping/mart_to_ybt_generator.py`
6. `backend/app/services/recommendation/source_field_recommender.py`
7. `backend/app/services/mapping/exporter.py`
8. `backend/app/services/deliverables/`
9. `backend/app/api/scenario_mappings.py`、`mapping_rules.py`、`deliverables.py`

### 理解的思想

- 业务主线是 Source→Mart→YBT 双层口径，不是让 AI 生成 SQL。
- AI 只更新 `ai_generated_content` 和草稿字段，不覆盖 `final_content`。
- `_physical_value_allowed` 使模型不能凭空写物理 schema/table/field。
- 证据直接绑定 mapping；审核通过要求 final_content 和证据。
- 导出/交付是最终产品，AI 只是生产过程中的辅助能力。

### 要主动发现的缺口

- 生成器中 Prompt 拼接和输出字段映射较紧，可引入统一 GenerationPipeline。
- 模型返回字段的严格 Schema 和错误策略不足。
- 置信度仍有模型自报成分，应改为证据规则/校准结果。
- Prompt 模板的 `user_template` 没有在所有生成器中统一使用。

### 你应做的改造

抽取统一的 `EvidenceGroundedDraftService`：检索、构造 Prompt、调用、Schema 校验、业务校验、日志和保存由固定模板编排；业务/技术输出使用不同 Schema 和 validator。

### 面试表达

> 我们把 AI 定位为草稿生成器，而不是口径最终裁判。业务口径和技术溯源分开建模，来源到集市、集市到一表通分两层；模型不能输出可执行 SQL，也不能覆盖人工最终值。物理字段必须在数据目录中验证，草稿要绑定证据并经过审核后才能进入交付包。

## 第四步：Agent 化改造

### 先读可复用工具

1. `backend/app/services/metadata/catalog_service.py`
2. `backend/app/services/retrieval/hybrid_retriever.py`
3. `backend/app/services/lineage/resolver.py`
4. `backend/app/services/lineage/impact_analyzer.py`
5. `backend/app/services/db/safe_sql_executor.py`
6. `backend/app/services/governance/workflow.py`
7. `backend/app/services/auth/permission_service.py`
8. `backend/app/services/auth/resource_guard.py`
9. `backend/app/services/task_queue/`

### 目标模块建议

```text
backend/app/services/agent/
  state.py
  tools.py
  planner.py
  executor.py
  validators.py
  field_caliber_agent.py
  trace.py
```

### 理解的思想

- 外层治理流程保持确定性，Agent 只在证据收集和缺口分析中动态决策。
- 工具复用现有 service，不能让 Agent 绕过权限直接访问 ORM。
- `SafeSqlExecutor` 只能封装成固定探查工具，不开放任意 SQL。
- Agent 结果仍写 `ai_generated_content`，并创建现有 Question/ReviewTask。
- Agent 运行状态适合异步 BackgroundJob，要求幂等和可恢复。

### 第一版边界

- 单 Agent，最多 8 步。
- 只读工具自动执行；`create_open_question`、`save_draft` 为受控写。
- 不引入多 Agent 和框架，先建立可测试状态机。
- 每步记录 decision code、tool、结果 ID、耗时和预算。

### 面试表达

> Agent 化不是把原有代码换成框架。我复用知识检索、目录、血缘和问题工作流作为最小权限工具，模型只选择有限动作；Executor 每次校验项目权限和参数。外层仍是固定审核流程，步骤、成本、循环和停止条件由代码控制。这样既获得动态取证能力，又不牺牲银行系统的可预测性。

## 第五步：评测

### 阅读顺序

1. `backend/app/services/evaluation/rag_evaluator.py`
2. `backend/app/api/knowledge_rag.py` 中 evaluation endpoints
3. `backend/tests/test_knowledge_rag.py`
4. `scripts/performance_baseline.py`
5. `scripts/smoke_test.py`
6. `frontend/app/evaluations/`

### 理解的思想

- EvaluationCase 是长期资产，不能只在发布前临时造。
- RetrievalLog 保存候选 ID，使检索问题与生成问题可分离。
- 当前已有 Recall@5/10、MRR、来源/表/字段命中、citation coverage、groundedness、延迟。
- 线上反馈不能直接当真值，需要审核后回流。

### 要主动发现的缺口

- groundedness 当前是粗粒度二值规则。
- 缺少 prompt/model/retrieval 配置的基线对比和显著性。
- 缺少 Agent tool selection、轨迹、成本和安全指标。
- 缺少按场景/问题类型的切片看板。

### 你应做的改造

为每次 EvaluationRun 固化 `code_commit + prompt_version + model_profile + embedding_version + retrieval_config + dataset_version`，生成基线差异报告并设置发布阈值。

### 面试表达

> 我把评测拆成解析、检索、生成、Agent 和系统五层。比如 Recall@K 低是召回问题，Recall 高但答案错是生成或证据使用问题。每次运行固化模型、Prompt、embedding、检索和数据集版本，结果按问题类型切片；安全指标和物理字段幻觉是硬门禁，不能用平均分掩盖。

## 第六步：权限、审核、UAT 与可观测性

### 阅读顺序

1. `backend/tests/test_governance.py`
2. `backend/tests/test_uat.py`
3. `backend/app/services/auth/permission_service.py`
4. `backend/app/services/auth/resource_guard.py`
5. `backend/app/services/governance/workflow.py`
6. `backend/app/services/governance/audit.py`
7. `backend/app/services/uat/`
8. `backend/app/core/observability.py`
9. `backend/app/services/task_queue/celery.py`
10. `docs/deployment/security-checklist.md`

### 理解的思想

- 认证、授权、资源归属和数据分类是四件事。
- 审核保存决定与内容快照；高风险血缘变更自动触发工作流。
- request_id/correlation_id 串联 API、后台任务和审计。
- UAT 不是“前端点一点”，而是可执行检查、Finding、签署和交付门禁。

### 面试表达

> 企业 AI 上线的完成条件不是生成成功，而是正确的人在正确的数据范围内得到可审核的草稿，并能回放全过程。项目用项目级权限、五阶段工作流、只追加审计、UAT 和后台任务状态形成治理闭环；下一步把 Agent trace 与现有 request、retrieval、model、audit log 串成统一链路。

## 源码学习完成标准

- 能从一个 HTTP 请求讲到数据库、检索、模型和审核。
- 能指出至少 10 个真实文件、3 个设计亮点和 5 个当前缺口。
- 完成三个可量化改造：严格结构化输出、RRF/rerank 实验、字段 Agent 原型。
- 所有表达区分“当前已实现”和“计划升级”，不夸大。
