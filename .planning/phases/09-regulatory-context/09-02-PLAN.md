## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| request payload to Pydantic | Caller-controlled ids, dates, mode, labels, limits, and nested values enter the contract. |
| ORM/retrieval data to contract | Existing rows and retrieval results are projected into bounded typed values and provenance. |
| contract to downstream builder/API | Serialized facts become a stable wire contract consumed by later plans. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-02-01 | Information disclosure | ContextScope and ContextProvenance | high | mitigate | Never accept a client institution override, require project-scoped identifiers, bound source references, and test cross-scope provenance handling. |
| T-09-02-02 | Tampering / repudiation | ContextFact authority and FactState | high | mitigate | Keep rank and lifecycle state separate, reject retrieval or inferred confirmation, and keep the four unclassified/unresolved spec-less records as test/plan metadata only rather than product facts. |
| T-09-02-03 | Tampering | EffectivePeriod and date validators | medium | mitigate | Normalize dates, enforce inclusive date ordering, and test invalid intervals before any builder or API consumes the schema. |
| T-09-02-04 | Information disclosure | bounded section values and ORM conversion | high | mitigate | Use `extra="forbid"`, discriminated bounded values, explicit provenance fields, and tests that reject ORM objects and arbitrary JSON dumps. |
| T-09-02-05 | Denial of service | nested values, fact lists, question lists | medium | mitigate | Apply maximum lengths and collection limits at schema boundaries, require explicit candidate mode, and reject unbounded payloads before query execution. |
</threat_model>
