用“图书馆”记住 4 个核心词

Embedding：编坐标→ Vector Store：存坐标、找近邻→ Retrieval：取证据→ LLM：依据证据写回答

LLM

Large Language Model，大语言模型。像写作员，负责理解问题并组织答案。DeepSeek Chat 属于这一层。

Embedding

嵌入/向量化。像图书管理员给每段文字编一组“含义坐标”。含义接近的文本，坐标应更接近。

Vector Store

向量存储。保存这些坐标，并快速查找与问题坐标最相近的 Top-K 记录。Milvus 是本项目已适配的正式实现。

RAG

Retrieval-Augmented Generation，检索增强生成。先从知识库检索证据，再让 LLM 依据证据回答。

Mock 到底是什么意思

Mock 可译为“模拟实现”或“测试替身”。它保留真实组件的接口，让整套系统在没有外部模型、密钥或向量数据库时仍能开发、测试和演示。

Mock 不是报错，也不等于真实能力。它说明流程接线可以验收，但不能据此评价真实大模型质量或生产级语义召回能力。

Mock LLM

返回代码里预设的固定结构化答案，不调用 DeepSeek，也不消耗 Token。

Mock Embedding

当前源码用 SHA-256 把文本稳定地变成 64 维数字。它可重复，但不真正理解中文语义。

Mock Vector Store

把向量保存在当前 Python 进程的内存字典里。进程重启会丢失，而且 API 与 Celery Worker 之间不共享。

为什么现在仍能检索到 Excel

本项目不是只靠向量搜索，而是混合检索：

PostgreSQL 关键词索引+ Mock 向量分数+ 监管答疑等规则加分→ Rerank 重新排序

上传的知识单元、来源文件、工作表、单元格范围和关键词索引都真实保存在 PostgreSQL。因此即使向量得分是 0.00，精确关键词仍能召回本地 Excel 内容。

三个容易混淆的组件

PostgreSQL

正式关系数据库，保存项目、知识单元、任务、日志、权限及关键词索引。

Redis

高速键值存储；当前主要作为 Celery 的消息 Broker 和结果后端。它不是本项目的向量数据库。

Celery Worker

后台工作进程，负责文档解析、批量索引等耗时任务，避免前台请求一直等待。

从当前模式升级到正式语义检索

  1. 激活 DeepSeek Profile，只会升级“聊天模型/答案生成”这一层。
  2. 另行配置真实 Embedding Provider 和 Embedding 模型。
  3. 启用共享、持久化的 Milvus 向量存储。
  4. 对现有知识文档重新索引，生成同一维度的新向量并写入 Milvus。
  5. 用 RAG 评测比较 Recall@K、MRR、引用覆盖率和回答正确性。

只配置 DeepSeek，不会自动把 Mock Embedding 和 Mock Vector Store 变成正式模式。

闭卷自测

Mock 是不是系统故障？

不是。它是主动选择的测试替身；流程可运行，但不代表真实 AI 或生产语义检索能力。

为什么向量得分为 0，仍能搜到 Excel？

因为 PostgreSQL 的关键词索引和规则重排仍在工作，当前结果主要来自关键词召回。

激活 DeepSeek 后，Embedding 会自动变真实吗？

不会。聊天模型与 Embedding 是两套独立 Provider，向量存储又是第三套配置。
