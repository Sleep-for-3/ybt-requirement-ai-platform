从一次口径生成看懂 LLM 调用链

今天只拿下一个结果：你能从业务生成器一路追到模型请求和调用日志，并说出三个企业级控制点。

任务

假设用户为一个字段场景点击“生成业务口径草稿”。请沿下面的链路阅读源码，不要横向浏览整个项目。

Generator→ PromptRuntime→ LLMService→ Provider→ ModelCallLog

按顺序打开 5 个文件

1. 业务入口

backend/app/services/mapping/scenario_draft_generator.py

找 generate_business_draft：它先取字段和场景，再检索证据，最后调用模型。

2. Prompt 运行时

backend/app/services/llm/prompt_runtime.py

找 get_prompt_runtime、prepare_model_input 和 record_model_call。

3. 抽象接口

backend/app/services/llm/base.py

观察业务代码为何只知道 chat_json，而不知道具体供应商。

4. 供应商适配

backend/app/services/llm/openai_compatible.py

找 temperature、JSON mode、timeout 和 fallback；区分“合法 JSON”与“业务 Schema”。

5. 可复现测试

backend/tests/test_llm_gateway.py

观察 Mock 如何让 CI 不依赖真实密钥和网络。

你应看到的三个架构思想

模型是可替换依赖

LLMService 把供应商差异封装在适配器后面。生成器依赖稳定接口，模型可以替换，业务规则不随 SDK 漂移。

敏感数据在外发前控制

prepare_model_input 根据本地/外部模型和敏感等级阻断或脱敏。权限不是写在 Prompt 里请模型自觉。

每次生成都必须能追溯

ModelCallLog 关联项目、Prompt 版本、模型和 RetrievalLog。以后出现错误口径，才能回答“当时用了什么证据和配置”。

主动找缺口：当前 JSON mode 不是严格 JSON Schema；Token usage 仍为空；temperature 固定而 top-p 未显式记录。这三个缺口就是第一轮改造候选。

闭卷自测

为什么要有 Mock LLM？

验证接口、状态和业务护栏，保证 CI 可复现且不依赖网络/密钥。它不能代替真实模型质量评测。

为什么 response_format=json_object 仍不够？

它最多保证 JSON 可解析，不保证字段、类型、枚举、citation 和物理字段符合业务契约；仍需 Pydantic 与业务验证器。

temperature=0.2 为什么不能保证口径正确？

温度只调采样随机性，不验证事实。正确性来自可见证据、目录/血缘校验、拒答和人工审核。
