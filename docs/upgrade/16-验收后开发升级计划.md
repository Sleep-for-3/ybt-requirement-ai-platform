状态：验收后版本迭代基线（待修复项清单）

适用范围：数据血缘与监管需求终版升级执行规格、当前工作区代码和本轮回归结果

## 1. 结论先行

本轮建议结论为：**有条件通过，不建议直接作为生产发布批准**。

已验证的本地能力较完整：后端全量回归 `541 passed, 5 warnings`；前端生产构建退出码 0；前端全量测试 `114 passed`；全新 SQLite 从空库迁移到 `202609100025` 成功；`scripts/smoke_test.py` 在本地 Uvicorn + 全新 SQLite + Mock LLM 环境退出码 0。

但上述结果不能替代生产门禁。当前仍存在迁移历史不可信、部分 API 参数只回显不生效、需求快照未成为交付渲染事实源、跨项目字段存在性查询、批量仓库同步产生中间态版本、生产 compose 缺少 Beat 进程，以及前端审计能力不完整等问题。至少完成 R1、R2、R3 的阻塞项并取得 PostgreSQL/生产配置证据后，才建议进入生产候选。

## 3. 验收矩阵

### 3.1 已满足或在本地夹具中通过

- 语义目录、语义详情、项目/机构隔离和受限引用脱敏。
- 需求工作台的结构化投影、血缘/证据/待确认/文档预览 tabs，以及人工最终内容优先。
- 本地 SQLite 全链路：脚本版本、字段级血缘、影响分析、审核任务、交付导出和 UAT。
- 覆盖率分子/分母可追溯，AI suggestion 不计入正式覆盖率；空分母返回 `null`。
- 数据质量期望和语义影响分析的既有 API/测试存在，且后端回归通过。

### 3.2 部分满足，需要版本迭代

- `view=business|technical` 已进入路径响应，但路径节点构建仍主要使用业务优先 DTO，技术视图没有独立投影契约。
- 项目图接口接受 `direction`、`depth`，但在选定 revision 时直接截断整张 revision 图，没有按根节点方向/深度遍历。
- 星云已支持版本选择、分层和同一响应驱动的图/表，但缺少 revision diff 时间线、字段/表级切换和可点击边详情。
- 需求快照已不可变持久化，但交付生成仍从 `DeliverablePackageVersion.content_snapshot_json`/实时 `_package_records()` 读取。
- 缺口建议已带 `approval_status=pending_review`，但只存在快照 JSON，没有持久化审批实体和批准 API。
- Phase 13 覆盖率已落地，但项目级 conflicts 仍未持久化，驾驶舱不能聚合冲突事实。

### 3.3 未满足或生产前阻塞

- 初始 migration 使用当前 `Base.metadata.create_all()`，历史 revision 不能代表历史 schema。
- `_source_field_in_catalog()` 查询 `CatalogColumn`/`SourceField` 未限定 `project_id`，同名资产可能跨项目命中。
- 仓库批量同步在每个文件 ingest 后构建一次项目 revision，可能发布 N 个中间态图版本。
- `docker-compose.yml` 仅启动 Celery worker，没有单独启动 Celery Beat；受控仓库轮询不会自动运行。
- 前端缺少完整审计交互：revision diff/时间线、边详情（SQL/Join/Filter/转换/证据）和传统分层 DAG。

## 4. 问题清单与修复要求

### P0：迁移历史可信度

证据：`backend/alembic/versions/202607070001_initial_schema.py` 导入当前模型后执行 `Base.metadata.create_all()`；历史探针显示早期 revision 已包含未来表/列。

修复：采用真实历史 DDL 重写初始迁移，或建立受控基线并明确旧数据库迁移策略；禁止用当前 ORM metadata 生成历史 schema。必须在 SQLite 与 PostgreSQL 分别验证：空库到 head、支持版本升级到 head、head 降级再升级、失败恢复和数据保留。

验收：`alembic history` 与每个支持版本的 schema 快照一致；新增回归用例证明 `202607070001` 不含 2026-08/09 才引入的对象。

### P1：血缘查询契约

证据：`backend/app/api/lineage.py` 的 revision 图分支调用 `_revision_graph_payload()`，其参数只有 `limit/layer`；`direction/depth` 仅回显。

修复：二选一并写入 API 契约：移除误导参数并声明“revision 全图”，或增加 `root_type/root_id` 并复用有界遍历，返回真实截断原因、预算和遍历范围。路径 resolver 为 business/technical 建立不同字段投影；技术视图主标题必须为技术标识。

验收：同一 revision 在 upstream/downstream/both 和 depth=1/3 下返回可观测差异；business/technical 的节点主标题和辅助字段有契约测试。

### P1：项目隔离与快照交付

证据：`backend/app/services/requirement_snapshot.py:1046-1083` 的来源字段查询没有 `project_id`；`backend/app/api/deliverables.py` 的 `_package_records()` 与 `_package_snapshot()` 未读取 `StructuredRequirementSnapshot`。

修复：为来源查询传入并限定项目/机构；缓存 key 也必须包含 project。为交付包增加 `snapshot_id`、快照 hash、血缘 revision 和语义版本绑定；生成、预览、审核、下载全部从指定不可变快照读取，保留旧导出兼容迁移。

验收：两个项目创建同名表/字段时不会互相命中；快照生成后修改实时 mapping 不改变历史渲染；指定 snapshot/revision 可重放同一交付内容。

### P1：仓库同步原子性与生产调度

证据：`ScriptIngestionService.ingest()` 每个文件后调用 `LineageRevisionService.build()`；`_ingest_files()` 逐文件提交。`backend/app/workers.py` 定义 beat schedule，但 compose 的 worker command 没有 `celery beat`。

修复：批量解析阶段先写文件事实和变更集，全部成功或按策略完成后只构建一次项目 revision；失败时保留上一 published revision，并记录 batch/commit manifest。生产 compose 增加独立 beat 服务或正式外部调度器、健康检查和重复调度防护。

验收：N 文件同步只产生一个批次 revision；任一文件解析失败不会发布部分图；beat 能在干净环境按周期投递一次且重复运行幂等。

### P2：审计细节、建议审批、冲突和质量债务

- 字段重命名：`revisions.py` 同时生成 `node_removed/node_added` 与 `field_renamed`，应在成功匹配后抑制重复项或建立关联组，并覆盖误匹配阈值。
- 缺口建议：新增持久化 `GapRecommendation`（snapshot/revision/evidence 关联、pending/approved/rejected/expired），实现批准/驳回 API，禁止自动写入事实。
- 冲突指标：建立项目级冲突事实投影，或在 UI 明确不可聚合；禁止伪造 0。
- 前端质量：清理构建中的 Hook 依赖警告，修复浏览器测试退出时的 CDP 子进程终止和临时 Profile `EBUSY` 清理。
- 文档追溯：同步 `.planning/REQUIREMENTS.md` 的 WRK/DSH/DQA/IMP 状态与实际阶段证据，避免与“全部完成”的终版报告冲突。

## 5. 版本迭代分期

### R1：迁移、安全与生产基线（发布阻塞）

目标：恢复 schema 历史可信度，补齐跨项目隔离，建立 PostgreSQL 和生产配置验证。

范围：迁移重构、scope 查询审计、数据库矩阵、真实 secret/config 检查、回滚演练。

门禁：空库/升级/降级/失败恢复通过；PostgreSQL smoke 通过；跨项目同名资产隔离测试通过；无高危迁移缺陷。

回滚边界：迁移发布前保留数据库备份和明确的 down/forward 方案；不得使用删库或覆盖 volume 的回滚方式。

### R2：血缘契约与版本原子性

目标：让 direction/depth/view 成为真实语义，并使批量仓库同步产生原子 revision。

范围：图/路径 API、business/technical DTO、批次 manifest、revision publish gate、重命名 diff。

门禁：方向/深度差异测试、技术视图测试、N 文件单 revision 测试、失败不覆盖 published 测试、7 类脚本变化夹具全通过。

回滚边界：保留旧路径/脚本上传兼容路由；新 revision 构建失败只能回到上一 published revision。

### R3：需求快照交付闭环

目标：快照成为交付渲染唯一事实源，并完成缺口建议人工审批闭环。

范围：DeliverablePackage 与 snapshot/revision/semantic version 绑定、渲染器、历史回放、GapRecommendation、审计。

门禁：快照不可变重放、实时事实变更不污染历史交付、批准/驳回/过期可审计、旧 Markdown/Excel 兼容。

回滚边界：旧交付包版本可下载；新快照字段采用可选迁移并支持回填/只读兼容。

### R4：前端审计与质量收敛

目标：补齐版本 diff、时间线、字段/表级切换、边详情和可访问性，并清理质量债务。

范围：`frontend/app/lineage/nebula`、`LineageNebula`、`LineageGraph`、浏览器测试 harness、Hook 依赖。

门禁：图/表/导出同源；边详情显示 SQL/Join/Filter/转换/证据；键盘访问、降动画、空态、截断和权限状态均有 E2E；构建零 Hook warning。

回滚边界：前端功能开关保留旧血缘列表视图；不改变后端事实模型。

### R5：生产验证与上线候选

目标：在 PostgreSQL、Celery/Beat、真实规模脱敏数据和受控仓库上完成候选发布验证。

范围：生产 compose、健康检查、调度、备份恢复、并发/容量、真实仓库轮询、监控告警和 runbook。

门禁：PostgreSQL migration/replay、worker+beat、真实仓库批量同步、备份恢复、权限隔离、Smoke/UAT/回归全部留存证据；无 P0/P1 未关闭。

## 6. 测试与发布门禁

