## 2. 两阶段边界

| 阶段 | 执行模型 | 交付目标 | 边界 |
| --- | --- | --- | --- |
| A：核心工程 | GPT-6 Astra | 能运行、能验证、可续做的 Skill 核心；完成权限、版本、发布门禁、证据链和高风险业务保护 | 不以只有设计文档或只有后端 CRUD 作为完成；需要代表性纵向闭环 |
| B：产品化与扩展 | GPT-6 Sol，其他模型仅在用户选择后使用 | 基于冻结接口完成完整页面、剩余业务接入、P2 增强和最终验收 | 不自行重做核心模型、权限或发布语义；新架构难点回到 Astra 定向处理 |

模型指开发时使用的 Codex 模型，不是强制把业务系统的 ModelProfile 改为 Astra/Sol。Plus 订阅也不代表业务系统已经具备真实模型 API 凭据。

## 3. 阶段 A：按依赖串行执行

下列是工作包，不是额度窗口承诺。一个工作包可以跨多个窗口；一个窗口也可完成多个很小的闭环。每次默认只领取一个最小可验证切片。

| --- | --- | --- |
| A0 基线与契约 | 盘点 Prompt key、调用方和 P0 复用项；定义 Skill/task key、输入信封、稳定证据 ID、四级范围解析、角色矩阵、运行状态；列出逐项文件落点和迁移增量 | 基线定向测试；契约样例与负例；现有字段复用清单；首批调用方迁移表；不重复新增已有 context_hash 等字段 |
| A1 版本与控制面 | 定义/版本/绑定/事件及兼容迁移；草稿并发控制、状态机、提交、发布、停用、恢复；旧 Prompt 快照与 API 兼容 | 跨租户拒绝；发布版本内容不可变；恢复生成新草稿并重新过门禁；发布/绑定/快照事务失败回滚；SQLite 与隔离 PostgreSQL 迁移 |

| A5 需求与 Mapping 保护 | 接入需求候选及四类 Mapping 的公共安全链路；固定输入版本、引用保存、物理字段白名单、草稿并发锁、人工内容保护、建议差异；固定修订导出一致性 | 四类 Mapping 均有契约测试；重生成不覆盖人工内容；跨脚本/多目标/歧义用例；Word 与 Excel 读取同一固定修订 |
| A6 复杂扩展参考实现与交接 | RAG 条款检索/效力比较/结构化冲突/答案验证的代表性实现；字段候选召回与重排接口及白名单；变更事件→影响路径→幂等复核任务；确定路由/缓存隔离契约 | RAG 失败保留证据；候选无法越出白名单或自动成为正式映射；历史需求不变；跨租户缓存拒绝；契约、固定样例和接入说明可供 Sol 复用 |

A1 在 A3 门禁完成前只允许开发/测试，不能提供绕过门禁的可用正式发布路径。A4 先具备有效条款获取能力，A6 再完善检索质量，不能让血缘核心依赖尚不存在的制度输入。

A6 不要求 Astra 完成全部检索优化与页面，但不能把未经实现验证的核心算法、权限或跨模块事务留给 Sol“自行设计”。无法接入真实 Embedding/重排 Provider 时，接口与固定回放测试可以交接，真实效果必须保留为未验证。

### A0 需要固定的决策

建议默认：项目管理员可创建/测试/提交草稿，正式发布由有权机构或平台审批人执行；实际权限标识复用现有 PermissionService。平台版本不得包含租户数据。运行详情默认保存摘要、哈希和可授权恢复的证据引用；完整输入保留策略需明确。首批不做跨机构配置包导入导出；RAG 评测先保留原入口，用统一导航关联。

此外必须明确：停用版本后解析与降级行为；绑定优先级；发布的审批、测试和内容哈希关系；模型/Profile 变化如何使测试过期；缓存键的机构/项目/版本/模型/知识版本/密级组成，以及命中时重新鉴权。将这些决策写入实施报告，Sol 不自行更改。

## 4. Astra → Sol 交接门禁

只有以下全部满足，才能标记 `ready_for_sol=true`：

1. A0～A6 的核心验收已通过，或具体外部模型依赖已标为未验证且不会绕过服务端门禁。
2. API、Schema、状态机、权限矩阵、输入/输出样例、错误码、迁移和兼容策略有具体代码及文档定位。
3. 血缘纵向流程在真实 API + Mock Provider 环境可运行，有浏览器证据；不能仅有路由 Mock 截图。
4. 版本不可变、范围隔离、过期测试拒绝发布、超预算阻断、引用校验、人工内容保护和固定版本导出有自动化证据。
5. 高风险未决问题为零；真实模型可用性与效果单独列项。外部依赖未验证时可交接开发，但不能宣称全部验收或上线可用。
6. 报告写清剩余 B 工作包、接口示例、允许修改范围、禁止修改的核心契约，以及失败后如何定位。

“A 阶段核心完成”“可交给 Sol”“第二部分全部完成”是三个不同状态，不得互相替代。

## 7. Plus 额度与续做方式

官方说明 Codex 用量受任务大小、复杂度和上下文影响，短窗口与周额度均需关注，不能把窗口长度当成可用计算时长。参考：[OpenAI Codex 用量与定价](https://learn.chatgpt.com/docs/pricing)。

本次查询账号为 Plus，工具返回五小时额度剩余约 94%、周额度剩余约 99%；这是查询时快照，返回的是 codex 额度桶，未提供 Astra 独立额度，不能推算可完成多少工作包。执行前应重新查询。

执行建议（工程策略，不是官方额度保证）：

1. Astra 默认使用 medium；涉及权限/事务/复杂算法时按实际难度提高推理强度。避免所有琐碎工作都使用最高强度。
2. 每轮读取实施报告和当前切片必要文件，不重复扫描整个仓库或历史日志。完成一个切片就先落盘，再考虑继续。
3. 每次开始记录工作区状态、当前工作包、基线和预期验证；长测试启动前也保存检查点。
4. 剩余额度约 20% 时优先收尾和定向验证，约 10% 时不新开大改动。这只是软提醒，不能保证能在限额触发前收尾；硬中断靠持续检查点恢复。
5. 每次保存：已修改文件、已过测试、未完成操作、后台进程/隔离环境、下一条命令。禁止把“正在跑”写成“通过”。
6. 额度恢复后由用户发送续做提示；无需每次另建任务。上下文已很长或更换执行模型时，可用落盘报告衔接，不依赖聊天记忆。
7. 五小时窗口恢复后仍需看周额度。切换 Sol 不能被承诺为绕过共享额度的办法。不自动兑换重置权益、不购买额度，也不创建定时任务。
8. 当前权限是 danger-full-access，按用户提供的代理约束，本方案默认主线程单代理串行执行，不启动受限角色子代理。如后续需委派，先满足对应权限前提及具体授权。

不承诺 A 阶段固定几轮完成。先执行 A0 和 A1 的最小切片，再用实际变更规模、测试耗时和额度消耗估算后续；不把七个工作包包装成七次五小时窗口。
