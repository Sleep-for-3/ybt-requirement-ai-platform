# R2 血缘契约与版本原子性报告

日期：2026-09-12
范围：血缘图接口语义、批量同步版本原子性、重命名 diff、前端契约一致性

## 结论

**R2 门禁通过。** 上一版列出的 4 条缺陷全部关闭，并补齐了对应的自动化测试；唯一仍然打开的是"真实规模脱敏仓库"的批量同步演练（属于验证范围，不是实现缺口），已登记到发布检查清单。

## 1. direction / depth / view 的真实语义（已关闭）

上一版问题：接口回显 `direction`/`depth`，但没有按根节点做真实遍历，前端因此会误报"已按方向过滤"。

当前实现：

- `backend/app/api/lineage.py`：`root_type` + `root_id` 同时存在时才做有界遍历（`_bounded_revision_traversal`，`depth` 限制 1–10）；只给 `direction`/`depth` 而不给根对象时返回 422，而不是静默回显。
- 全量版本快照模式在响应里明确 `mode="revision_snapshot"`，并声明方向与深度未应用。
- 节点/边预算被截断时返回 `truncation_reason`（`depth_limit` / `node_budget` / `edge_budget`）。
- `backend/app/services/lineage/view_projection.py` 提供 business / technical 两种投影（`project_nodes`、`validate_view`），同一批事实按视图产出不同 DTO，而不是靠前端改名。
- 前端 `frontend/lib/lineage-graph.mjs` 的 `describeTraversal()` 把上述三种模式翻译成不同文案：快照模式绝不声称"方向 upstream 已生效"。

证据：

- `backend/tests/test_lineage_graph_contract.py`（**8 passed**）：有界遍历方向深度、下游遍历可达、缺根对象被拒而不是回显、快照模式不冒充已应用、业务/技术视图投影差异、跨项目根不可见、节点预算截断原因、路径接口应用所选视图。
- `frontend/tests/lineage-graph.test.mjs`：Node DOM 测试直接验证运行时 `.mjs` 契约。

## 2. 批量同步的版本原子性（本轮完成）

上一版问题：仓库/压缩包批量同步可能"逐文件"构建 revision，一个批次产生几十个版本，失败文件会污染已发布版本。

改动：

- `backend/app/services/lineage/ingestion.py`：`ingest(..., build_revision: bool = True)`。批量调用传 `False`，把建版本的责任交给调用方，单文件路径行为不变。
- `backend/app/services/lineage/jobs.py`：
  - `_ingest_files(..., build_revision=True)` 汇总批次事实 `batch_facts`（ingested_count / failed_count / skipped_completed_count / parse_status_counts / worst_severity）；
  - 新增 `batch_revision_gate(batch_facts, review_required)`：任一文件失败、非 `parsed`、或含 medium 及以上风险变更时**不自动发布**，批次置 `needs_review` 并保留上一个 published 版本；
  - `ingested == 0`（重跑幂等）时不新建 revision，直接返回当前 published 版本号；
  - `script_repository_sync_handler` 在 ingest + 重命名 + 删除**全部完成后只建 1 个 revision**（`trigger_type="repository_sync"`）。

证据：`backend/tests/test_lineage_batch_sync.py`（**4 passed**）——zip 一批只产生 1 个 revision、重跑幂等不新增版本、失败批次不覆盖 published、仓库同步 ingest+rename+delete 合并为 1 个 revision。

## 3. 重命名 diff 去重（本轮完成）

上一版问题：字段重命名会同时产生 `node_removed`、`node_added`、`field_renamed` 三类记录，审阅者无法判断到底是改名还是换字段。

改动：`backend/app/services/lineage/revisions.py` 新增 `_match_renamed_nodes()`，做一对一贪心匹配（相似度阈值 `_RENAME_SIMILARITY_THRESHOLD = 0.65`），命中后只输出重命名记录并带 `match_confidence`，不再同时产生新增/删除。

证据：`backend/tests/test_lineage_revisions.py`（**7 passed**，含新增的相似度阈值与去重用例）。合并运行 `test_lineage_batch_sync.py + test_lineage_revisions.py` 为 11 passed；叠加 `test_lineage_monitoring.py + test_sql_lineage.py` 为 38 passed。

## 4. 与发布编排的关系

Celery beat 的 `lineage-repository-monitor` 已在真实 Redis/PostgreSQL 演练中启动并产生调度日志（见 `docs/upgrade/R5-生产验证与上线候选报告.md`），但尚未观察到一次"真实仓库轮询 → 批次发布"的完整结果，因此该项在发布检查清单中仍记为部分完成。

## 5. 未验证范围

- 真实规模脱敏仓库（文件数、体积、并发）下的批量同步表现：**未验证**；
- 大批次并发同步、队列积压与告警阈值：**未验证**；
- 失败恢复演练（迁移/同步中断后的恢复路径）：仅覆盖降级与重建，中断恢复未演练。

以上三项不得在发布说明中表述为"已验证"。
