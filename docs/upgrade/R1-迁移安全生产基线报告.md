## 1. P0：迁移历史可信度（已关闭）

### 问题

`202607070001_initial_schema.py` 调用 `Base.metadata.create_all()`，因此：

- 全新库拿到的是"当前工作树"的结构，而不是 2026-07-07 的结构；
- 之后每个 revision 的建表语句都因表已存在而静默失效（no-op）；
- 迁移历史无法复现，新增模型列可能完全没有对应迁移。

### 修复方式：从 git 历史重建真实结构并冻结

历史 revision 与引入它们的 commit 严格一一对应（001→`ff1f41f` 2026-07-07 … 021→`b31faea` 2026-08-30）。据此：

1. `scripts/migration/_metadata_dump.py`：在 `git archive` 导出的历史检出中导入当时的 `app.models`，导出该时点真实的 metadata；
2. `scripts/migration/frozen_schema_gen.py`：按相邻 revision 求差，得到"每个 revision 真正新增了哪些表"，生成 `backend/app/schema_freeze/data.py`；
3. `backend/app/schema_freeze/runtime.py`：在迁移运行时把冻结数据还原为真实表（方言无关，SQLite 与 PostgreSQL 均可）；
4. 重写 7 个依赖当前 ORM 的迁移，改为使用冻结定义：
   - `202607070001_initial_schema.py`（12 张表）
   - `202607070002_template_datasource_nl_task.py`（5 张表 + 4 列）
   - `202607070003_double_layer_mapping.py`（9 张表）
   - `202607100004_scenario_traceability.py`（7 张表 + 9 列）
   - `202607140005_metadata_catalog_profiling.py`（8 张表 + 6 列）
   - `202607140006_knowledge_rag_evaluation.py`（13 张表 + 21 列）
   - `202607150009_sql_lineage_change_impact.py`（12 张表 + 9 列）
5. `backend/tests/test_migration_schema_freeze.py`：用 AST 断言任何迁移都不得导入 `app.models`、使用 `Base.metadata` 或 `globals()`；冻结数据必须与 Alembic 链顺序一致。

### 修复过程中暴露并修掉的真实缺陷

这些缺陷此前被 `create_all` 完全掩盖，只有真正执行历史迁移才会出现：

| 缺陷 | 影响 | 处理 |
|---|---|---|
| `knowledge_keyword_indexes` 没有任何迁移创建 | 全新库缺表 | 在 `202607150007` 用冻结定义补建 |
| 34 个列在历史迁移中被建成可空，ORM 要求 NOT NULL | 全新库约束弱于存量库 | 新增 `202609120026` 迁移修正，仅在该列无 NULL 时才收紧 |
| `202607140005` 用 `op.add_column` 加带外键的列 | SQLite 全新库直接失败 | 改为 batch 模式 |
| `202607150007` 把唯一约束当索引 DROP | PostgreSQL 回滚报 `DependentObjectsStillExist` | 跳过约束支撑的索引 |

- 迁移重构前必须保留数据库备份与旧 revision；
- 禁止删库、覆盖 volume 或破坏性 Git 回滚；
- 本次新增的 `202609120026` 只收紧可空性且带 NULL 保护，可在有数据的环境安全执行；`downgrade` 会恢复为可空。
