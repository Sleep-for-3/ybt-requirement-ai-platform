| D13 | 性能基线脚本**只能在 SQLite 上跑**，且 fixture 的外键链是悬空的：`lineage_edges.script_file_version_id` / `impact_analyses.change_set_id` / `background_jobs.created_by=0` 都指向不存在的行。SQLite 默认不校验外键，所以"基线通过"这一结论从未在真实数据库上成立过 | **规模类结论不可信**：真实 PostgreSQL 上脚本第一步就 `ForeignKeyViolation` 中断，等于没有真实库规模证据；同时掩盖了"脚本无法指向真实 PG"这一门禁缺口 | 新增 `--database-url` / `PERFORMANCE_DATABASE_URL`（非空目标库直接拒绝，避免污染真实数据；目标连接串按 `hide_password=True` 打印）；fixture 补齐"机构 → 用户 → 存储文件 → 脚本 → 脚本版本 → 变更集"链路，`background_jobs.created_by` 改指向 fixture 用户；结果新增 `database_dialect` 字段 | PostgreSQL 16.4 上 `--small` 与 FULL 规模均 `exit=0`（见下表）；`scripts/performance_baseline.py` |
| D14 | 单次生成的**最坏等待没有上界**：提供方预算 `LLM_TIMEOUT_SECONDS=120` 是"单次尝试"预算，实际耗时 = 120 s × (1+重试 2) × 兜底 2 个模型 ≈ 12 分钟；而前端所有请求共用 60 s 超时（`REQUEST_TIMEOUT_MS`）。真实模型下用户必然先看到"请求超时，请稍后重试"，服务端却仍在生成 → 用户重试产生重复草稿 | 真实模型下"生成类"操作对用户表现为**必失败**：既拿不到结果，也无法区分"慢"和"坏" | 前端新增按路径区分的请求预算 `frontend/lib/request-timeout.mjs`（默认 60 s / 生成、画像、同步、评测、渲染、下载、问答等长耗时端点 600 s），`api.ts` 统一走该策略；测试断言长预算 ≥ 实测最坏 411.6 s。**根治仍走 P1-6**（生成类接口改后台任务 + 轮询），届时可把长预算收回 | `frontend/tests/request-timeout.test.mjs`（4 例）、`npm test` **127 passed**、`npx tsc --noEmit` exit 0；真实证据：一次 `mart_to_ybt_mapping` 成功调用耗时 **411 624 ms**（PG16.4 + 真实模型，`model_call_logs`）|

> D5 的定位过程值得保留：第一次镜像构建成功后 API 反而崩溃，日志为 `ModuleNotFoundError: No module named 'app.services.storage'`。根因是 Docker 的目录模式按**任意层级**匹配。这正是"必须做一次真实打包演练"的价值。

| P2-4 | 开发容器自恢复 | WSL 发行版会被整体重启（本轮实测约每十几分钟一次），容器默认 `restart=no` 会静默停库。已将 `ybt-dev-*` 三个容器设为 `unless-stopped`（回退：`docker update --restart no ...`） |
| P2-5 | Smoke 脚本与跨容器数据源 | Smoke 用容器内临时 SQLite 作为数据源，在"API 与 Worker 分属两个容器"的真实拓扑下不可见；建议 Smoke 支持 `SMOKE_DATASOURCE_URL`（指向真实网络库），使同一脚本在开发栈与编排栈都能全量执行 |
| P2-6 | 演练宿主机稳定性 | 本机 WSL 发行版在演练期间反复整体重启（观测到 8 分钟一次，甚至 1–5 分钟一次），容器内的 API / Celery / Smoke 进程随容器一起被终止："真实 PostgreSQL + 真实模型"的全流程 Smoke 无法在单个窗口内跑完。本轮改用不依赖 WSL 的 Windows 原生栈完成端到端验收（`SMOKE_EXIT=0`）；**上线前须在稳定主机（生产预演机）补做该组合**，并保留一份完整的 `model_call_logs` 供审计 |
| P2-7 | Smoke 客户端超时 | 脚本固定 `timeout=90`，在真实提供方（单次 11–123 s）或 inline 队列下必然超时；已改为 `SMOKE_REQUEST_TIMEOUT_SECONDS`（默认 90），演练建议 900 |

## 2.1 真实 PostgreSQL 规模基线（2026-09-13，P0-2 的"规模"部分）

环境：本机 PostgreSQL **16.4**（EDB 便携版，`127.0.0.1:15434`，与生产同主版本），专用空库 `ybt_perf` / `ybt_perf_full`；`scripts/performance_baseline.py` 自带脱敏 fixture，不含任何真实机构或客户数据。

## 3. 环境与演练注意事项（非产品缺陷）

- 仓库根 `.env` 原本不存在，本轮为打包演练生成了**本地演练用** `.env`（随机密钥、gitignored）。上生产前必须整体替换为真实密钥；
- 本机 `.wslconfig` 设置 `networkingMode=mirrored` 且 `ignoredPorts=8000`，因此 Compose 发布的 `127.0.0.1:8000` 在 Windows 侧不可见；验证请在容器网络内进行；
- 真实环境容器固定使用主机名 `ybt-dev-pg` / `ybt-dev-redis`（`pg` / `redis` 会被本机代理解析成 fake-IP）。
- 本轮补充证据：宿主机 Hyper-V vSwitch 网卡连续重建（事件时间 22:06:55、22:07:03），容器 `Up` 时长反复回到 0–30 秒，而 `free -m` 显示 7.8 GiB 内存仅用约 0.9 GiB、交换区未使用——重启不是内存压力，而是 WSL 虚拟机被外部反复重启；Windows 事件日志未出现可直接归因的 LxssManager 报错。
- 本轮采用的规避方案（已验证）：把**应用栈**改为 Windows 原生 Python 运行（`TASK_QUEUE_PROVIDER=inline`），**数据库**改用本机独立 PostgreSQL 实例（scoop 安装的 18.4，数据目录 `backend/.smoke-run/pgdata`、`127.0.0.1:15433`，仅用于演练、不接触应用数据）。"真实 PostgreSQL + 真实模型"的全流程 Smoke 因此可在 501 s 内跑完并留下完整 `model_call_logs`。注意本机实例是 PostgreSQL **18.4**、生产是 **16**：迁移矩阵结构指纹已验证一致，但发布前仍须按 P0-6 在生产副本上复核。
- 真实提供方（含国产模型网关）单项超时与并发能力差异很大：`LLM_TIMEOUT_SECONDS` 建议按提供方实测设置为 120–180；演练脚本用 `SMOKE_REQUEST_TIMEOUT_SECONDS=900`。国产模型接入方式：`LLM_FALLBACK_MODELS` + `LLM_FALLBACK_BASE_URL` + `LLM_FALLBACK_API_KEY_ENV_NAME`（见 `.env.production.example`）。
- 生产同版本演练：本机另装了一份 **PostgreSQL 16.4**（EDB 便携版，`backend/.smoke-run/pg16`，`127.0.0.1:15434`），用于在"与生产同主版本"的库上复跑迁移矩阵与真实模型 Smoke，弥补本机 scoop 实例为 18.4 的版本差。所有实例都只服务于演练，不接触任何真实业务库。
- 会话续期演练参数：为了在可接受的时间内验证 D12，真实模型 Smoke 用 `ACCESS_TOKEN_MINUTES=5`（生产默认 15）加速令牌轮换，确保一次演练内发生**多次**续期，而不是只碰上一次。
- 演练期间发现真实模型 API Key 曾被调试日志意外写出（相关容器内日志文件已删除）。**上生产前请轮换该密钥**，并避免再用"把密钥写进文件/日志"的注入方式。
- 演练产生的可回收产物：`ybt_smoke`/`ybt_smoke2`/`ybt_smoke3`/`ybt_smoke4`/`ybt_smoke5`/`ybt_smoke6`、`ybt_restore_check` 数据库，`ybt-storage-restore-check` 卷，以及 `/home/lrw/ybt.dump`、`/home/lrw/storage-backup.tgz`（备份演练证据）。删除前请确认不再需要。
