# 智能分析智能体平台：数据血缘与监管需求终版升级执行规格

版本：V2.1/V3 规划基线

用途：本文件既是产品/架构规格，也是交给 Codex 执行的实施约束。执行前必须先完成仓库盘点，不得把本文中的示例对象当成已经存在的代码对象。

## 0. 先说结论

本次不是简单新增一个血缘页面，而是一次跨领域的重大平台升级，涉及：

- 技术脚本血缘；
- 表和字段版本；
- Source → 数仓 → 监管集市 → 一表通/EAST/1104 的端到端路径；
- 监管要求到结构化开发需求的映射；
- Join、Filter、转换和数据缺口建议；
- 业务中文名称优先展示；
- 血缘变更影响分析；
- 星云式可视化和审计视图。

产品上可以按 V2.1 或 V3.0 管理，工程上必须采用增量重构，不允许全量重写。

附件图片仅提供“深色星云、发光节点、粒子连线、中心聚焦”的视觉参考，不包含功能规则，也不能作为业务事实来源。

## 2. 当前缺口：本次升级真正要解决什么

### 2.1 技术血缘和业务口径还不是一条统一的端到端链

当前技术脚本会生成 `LineageNode/LineageEdge`，业务口径则存放在：

```text
ScenarioTechnicalLineage
SourceToMartMapping
MartToYbtMapping
TargetField
```

这些对象已经可以相互关联，但还缺一个统一的路径解析契约，无法稳定回答：

```text
某个监管字段
→ 哪个一表通字段
→ 哪个监管集市字段
→ 哪些数仓字段
→ 哪个源系统、哪张源表、哪个源字段
→ 使用了什么 Join、Filter、转换和版本
```

本次必须增加“路径投影/解析服务”，而不是再建第二套节点边表。

### 2.2 当前脚本版本不等于血缘图版本

`ScriptFileVersion` 和 `ScriptChangeSet` 可以记录脚本变化，但当前还缺：

- 某一时刻整个项目的血缘快照；
- 按历史版本查询图；
- 两个血缘版本之间的结构化差异；
- 需求文档所依据的血缘版本；
- 图版本发布、审核和回看机制。

必须区分：

```text
script_revision       脚本文件版本
catalog_revision      表、字段、备注和术语版本
lineage_revision      血缘语义图版本
requirement_version   结构化需求版本
```

脚本格式化变化不能被误报成血缘变化；脚本删除、字段来源变化、Join 变化和过滤口径变化必须产生可审计的血缘语义变化。

### 2.3 当前变更影响需要变成可操作的治理闭环

已有 `ImpactAnalysis`，但终版需要将影响继续投影到：

- 受影响的中文业务字段；
- 受影响的一表通指标；
- 受影响的 `SourceToMartMapping` 和 `MartToYbtMapping`；
- 受影响的 `SemanticConcept` 和监管规则；
- 受影响的需求文档版本；
- 待确认问题；
- 技术审核和最终审核任务。

高风险影响不能只显示红色数字，必须能点到具体字段、具体脚本、具体 SQL 行和具体审批任务。

### 2.4 当前需求文档仍需要结构化取数方案

现有导出已经包含业务口径、技术溯源、双层 Mapping、证据和问题，但终版必须将以下内容变成结构化数据，而不是只存在于长文本中：

- 来源系统；
- 来源表；
- 来源字段；
- 监管集市表和字段；
- 关联条件；
- 关联类型和基数；
- 时间对齐条件；
- 过滤条件；
- 聚合规则；
- 码值转换；
- 空值和异常处理；
- 数据质量校验；
- 当前缺口；
- 增加字段、增加表、桥接表或字典表建议。

### 2.5 当前业务名称展示缺少统一契约

有些模型已经保存了中文备注，但不同页面仍然可能直接展示 `logical_name`、`field_code`、英文物理字段或技术路径。

必须建立统一的显示 DTO 和解析服务，不要修改物理字段名来“伪装”业务名称。

### 2.6 交给 Codex 时必须重点核对的代码事实

以下不是假设，而是本次基线中应优先验证和处理的风险点：

- `backend/app/api/lineage.py` 的项目级图接口当前主要按项目批量读取节点和边；`direction`、`depth` 和 `limit` 的真实遍历语义必须重新核验，不能只把参数原样返回；
- `LineageNode/LineageEdge` 以脚本版本为证据来源，但项目图查询必须避免把多个历史脚本版本混成一个“当前图”；
- 当前脚本版本和 `ScriptChangeSet` 不能替代项目级 `lineage_revision`，需求文档不能只记录脚本文件版本；
- 当前 `ImpactAnalysis` 的若干影响范围使用 JSON ID 列表保存，详情接口必须补足业务显示名、路径、证据和版本，而不是只显示 ID；
- `RequirementWorkspaceProjectionService` 面向首屏性能会做摘要和懒加载，终版路径解析不能退化成只取第一条 Mart 或 Source Mapping；
- `frontend/components/LineageGraph.tsx` 当前是边表格，不能在不改 API 契约的情况下直接宣称已经实现图形血缘；
- 需求文档中的 `sourcePath`、`logical_name` 和字段代码需要统一接入业务显示 Resolver，不能在组件内各自拼接名称；
- 现有 `MappingVersion` 负责口径快照，不能被误用成技术血缘图版本；
- `formal semantic index` 的索引版本和业务血缘版本是两套完全不同的职责，不能合并命名或共享状态。

## 3. 目标架构原则

### 3.1 增量架构，不重复建模

以下对象继续作为权威事实：

- `SourceField`、`MartField`、`TargetField`、`CatalogColumn`：数据资产；
- `LineageNode/LineageEdge`：脚本解析出的技术血缘证据；
- `ScenarioTechnicalLineage`：场景级技术口径；
- `SourceToMartMapping`、`MartToYbtMapping`：双层业务取数口径；
- `SemanticBinding`：语义对象与已有事实的治理连接；
- `ImpactAnalysis`：变更影响结果；
- `DeliverablePackageVersion.content_snapshot_json`：交付快照边界。

不得新建一套与这些对象平行的 `DataAsset`、`DataField`、`NewLineageNode` 或 `NewMapping`，除非基线审查证明现有模型无法表达，并且必须先写 ADR 说明不能复用的原因。

### 3.2 确定性血缘核心 + 受控 AI 建议

大模型可以：

- 从监管文本提取条款、指标和业务术语；
- 对候选字段进行语义排序；
- 提出缺失字段、桥接表和字典表建议；
- 把结构化事实渲染成自然语言需求描述。

大模型不能：

- 凭常识创建不存在的表或字段；
- 直接修改已确认的血缘；
- 把候选映射自动变成正式事实；
- 绕过 `PermissionService`、`SafeSqlExecutor` 或审核流程；
- 直接执行用户上传的 SQL、Shell 或 Git hooks。

### 3.3 关系型权威存储，有限图查询

当前项目已经决定不引入 Neo4j、GraphRAG 或新的图数据库。继续使用 PostgreSQL/SQLite 的关系模型和有界遍历：

- 技术事实存关系表；
- 路径查询使用索引邻接和有界 BFS/递归查询；
- 星云看板消费经过限深、限节点和权限过滤的图 DTO；
- 只有在实际 benchmark 证明关系查询不足时，才评估图投影缓存。

## 4. 终版领域契约

### 4.1 统一资产显示对象

所有面向前端、导出和模型上下文的资产对象都应提供：

```json
{
  "id": 123,
  "entity_type": "source_field",
  "display_name": "客户统一标识",
  "business_name": "客户统一标识",
  "comment": "用于跨系统识别同一客户",
  "technical_name": "cust_id",
  "qualified_technical_name": "crm.customer.cust_id",
  "display_name_source": "field_comment",
  "label_quality": "confirmed",
  "layer_code": "SOURCE",
  "layer_name": "源系统",
  "system_name": "客户信息系统"
}
```

默认显示优先级：

```text
已确认业务名称 > 中文备注 > 业务别名 > 描述 > 技术字段名
```

技术名称永远保留，但作为次要信息、Tooltip、详情和开发视图显示。

### 4.2 统一血缘节点和边

血缘节点必须能指向已有权威实体，也允许暂时未解析：

```text
node_id
entity_type
canonical_entity_id
script_file_id
script_file_version_id
node_type
layer_code
display_label
technical_identifier
unresolved_flag
resolution_status
```

血缘边必须记录：

```text
source_node_id
target_node_id
edge_type
transformation_type
transformation_expression
join_condition
filter_condition
aggregation_rule
code_mapping_rule
source_line_start
source_line_end
confidence_level
verification_status
evidence_refs
```

建议的 `edge_type`：

- `projection`：直接投影；
- `rename`：字段重命名；
- `cast`：类型转换；
- `expression`：表达式计算；
- `join`：关联；
- `filter`：过滤；
- `aggregation`：聚合；
- `union`：合并；
- `lookup`：码表或维表查找；
- `script_dependency`：脚本依赖；
- `manual_binding`：人工确认关系。

### 4.3 血缘版本

如果现有模型不足，新增最小版本模型，而不是替换已有脚本版本：

```text
LineageRevision
  id
  project_id
  revision_no
  parent_revision_id
  trigger_type
  source_commit_sha
  parser_version
  graph_hash
  status: draft | needs_review | published | superseded | failed
  created_by
  created_at
  published_at
```

节点和边的历史归属可以采用以下任一种方式，但必须由 ADR 固定：

1. 血缘节点/边增加 `lineage_revision_id`；
2. 使用 `LineageRevisionNode` / `LineageRevisionEdge` 快照成员表；
3. 使用 `valid_from_revision` / `valid_to_revision` 区间。

优先选择不会覆盖旧数据、支持 SQLite/PostgreSQL、可按版本读取且迁移风险最小的方案。

### 4.4 统一端到端路径

新增路径解析服务，例如：

```text
LineagePathResolver.resolve(
  project_id,
  root_entity_type,
  root_entity_id,
  direction,
  depth,
  lineage_revision_id,
  include_unresolved
)
```

输出必须包含：

- 有序节点列表；
- 有序边列表；
- 每条路径的完整起点和终点；
- 当前层级；
- 中文业务名和技术名；
- Join、Filter、转换和证据；
- 置信度；
- 缺失节点和未解析节点；
- 是否截断；
- 对应版本。

路径解析需要桥接：

```text
TargetField
  ↔ MartToYbtMapping
  ↔ MartField
  ↔ SourceToMartMapping
  ↔ SourceField/CatalogColumn
  ↔ LineageNode/LineageEdge
  ↔ ScriptFileVersion
```

桥接关系必须经过项目权限和实体归属校验，不能只靠字符串拼接。

## 5. 脚本监控和变更处理

### 5.1 输入来源

继续复用当前能力，并补齐触发方式：

- Git 仓库受控同步；
- ZIP 或单脚本上传；
- 定时轮询；
- 后续可选 webhook；
- 调度平台导入的任务/脚本快照。

### 5.2 标准处理流程

```text
获取脚本快照
→ 校验路径、大小、扩展名和仓库白名单
→ 计算原始哈希和标准化哈希
→ 解析 SQL/Shell/ETL 依赖
→ 解析对象引用并尝试绑定现有资产
→ 生成候选血缘
→ 与上一脚本版本比较
→ 生成 ScriptChangeSet
→ 生成或更新 LineageRevision
→ 计算下游 ImpactAnalysis
→ 更新待确认问题和审核任务
→ 发布或保留上一版正式血缘
```

### 5.3 必须区分的变化

以下变化不能混为一谈：

- 仅空格、注释或格式变化：`non_semantic`；
- 文件路径变化：脚本非语义变化；
- 来源字段新增或删除：字段血缘变化；
- 来源字段重命名：需要生成重命名候选，不能简单显示为删除+新增；
- Join 条件变化：高风险；
- Filter 条件变化：高风险；
- 聚合或码值变化：高风险；
- 解析质量下降：至少需要人工审核；
- 脚本删除或仓库中消失：相关正式血缘标记 `stale`，不能静默删除。

### 5.4 解析失败原则

- 解析失败时保留上一版 `published` 血缘；
- 当前版本标记 `failed` 或 `partially_parsed`；
- 记录安全的错误摘要和源代码位置；
- 受影响链路进入待审核状态；
- 不执行脚本来“推断”血缘；
- 不把低置信度结果伪装成已验证关系。

## 6. 监管要求到开发需求的终版流程

### 6.1 输入

支持以下输入组合：

- 监管制度文本；
- 一表通目标模板；
- 目标字段定义；
- 报送周期和时间口径；
- 业务场景；
- 目标系统，例如一表通、EAST、1104；
- 业务术语和历史口径；
- 现有数据目录和血缘版本。

### 6.2 结构化中间对象

先生成并校验结构化对象，再渲染文档：

```text
RequirementClause
  条款、义务主体、指标、维度、时间、频率、约束、证据

RequirementFieldPlan
  目标字段、业务名称、技术名称、来源路径、转换、质量规则

JoinPlan
  左表、右表、左键、右键、Join 类型、基数、时间条件、空值处理

GapRecommendation
  缺口类型、问题、推荐增加字段/表/桥接表/字典表、理由、影响、置信度

StructuredRequirementSnapshot
  requirement_version、catalog_revision、lineage_revision、model_version、内容哈希
```

### 6.3 字段映射结果

每个目标字段至少要输出：

- 中文业务名称；
- 技术字段名；
- 目标表；
- 来源系统；
- 来源层级；
- 来源表；
- 来源字段；
- 完整血缘路径；
- 转换表达式；
- 过滤条件；
- 关联表和关联字段；
- 关联条件；
- 时间口径；
- 聚合口径；
- 数据质量规则；
- 证据和脚本行号；
- 当前是否满足；
- 待确认问题；
- 对应版本。

### 6.4 缺口建议

缺口建议必须是“建议”，不能直接修改生产模型。至少支持：

- 建议新增字段；
- 建议新增来源表；
- 建议新增监管集市表；
- 建议增加桥接表；
- 建议增加字典/码表；
- 建议增加统一业务主键；
- 建议增加生效日期、统计日期或快照日期；
- 建议调整数据粒度；
- 建议增加接口或数据同步任务。

每条建议包含：

```text
gap_type
problem_statement
recommended_change
alternative_options
rationale
evidence_refs
affected_assets
estimated_impact
confidence_level
approval_status
```

## 7. 前端终版设计

### 7.1 两种查看模式

#### 数据星云总览

- 深色背景和分层色带；
- 系统或业务域作为较大的“星球”；
- 表和数据资产作为节点；
- 字段作为聚焦后的子节点；
- 通过边上的粒子表达数据流方向；
- 节点颜色表达层级，边颜色表达状态；
- 支持按系统、层级、领域、版本、风险和状态筛选；
- 支持聚焦某个监管字段并显示完整路径。

#### 血缘审计详情

- 传统分层 DAG；
- 表级/字段级切换；
- 上游/下游/双向；
- 版本时间线；
- 新增、删除、修改边高亮；
- 点击边查看 SQL、Join、Filter、转换和证据；
- 未解析节点、低置信度和过期血缘单独显示；
- 同时提供表格模式，保证可审计和无障碍访问。

### 7.2 动效约束

- 动效只表达状态和方向，不表达未经证实的实时运行；
- 支持暂停和关闭动画；
- 尊重 `prefers-reduced-motion`；
- 节点数量大时使用渐进加载、聚合和虚拟化；
- 不为了 3D 效果引入不可维护的运行时依赖；
- 先完成 2D 分层视图，再评估可选 3D 总览。

### 7.3 业务名称规则

页面、卡片、节点、列表和导出默认使用中文业务名称。技术名称出现在：

- 次标题；
- Tooltip；
- 详情抽屉；
- 开发者模式；
- Excel/Markdown 技术列。

如果中文备注缺失，必须显示“缺少业务备注”状态，不要静默用英文名称冒充中文名称。

## 8. 建议的新增 API 契约

所有新增接口必须保持项目权限、机构隔离和旧接口兼容。以下路径是建议命名，Codex 必须先检查现有命名约定后再落地。

```text
GET /projects/{project_id}/lineage/revisions
GET /lineage/revisions/{revision_id}
GET /lineage/revisions/{revision_id}/diff?compare_to={revision_id}
GET /projects/{project_id}/lineage/path
    ?root_type=target_field
    &root_id=123
    &direction=upstream|downstream|both
    &depth=1..10
    &revision_id=...
    &view=business|technical
GET /projects/{project_id}/lineage/graph
    ?revision_id=...
    &layer=...
    &limit=...
POST /projects/{project_id}/lineage/rebuild
POST /projects/{project_id}/lineage/revisions/{revision_id}/publish
GET /projects/{project_id}/requirements/snapshots
GET /requirements/snapshots/{snapshot_id}
POST /projects/{project_id}/requirements/analyze
POST /requirements/gap-recommendations/{id}/approve
```

返回对象必须包含：

- `project_id`；
- `as_of` 或 `revision_id`；
- `truncated`；
- `warnings`；
- `confidence`；
- `evidence_refs`；
- 业务和技术双名称；
- 权限允许范围内的导航链接。

旧接口如 `/target-fields/{field_id}/lineage`、`/mart-fields/{field_id}/lineage`、脚本上传、变更集和影响分析接口不能删除或改变既有语义。

## 9. 实施阶段和门禁

### Phase 12：Structured Requirement Snapshot

目标：把当前需求工作台的事实、证据、血缘、问题和治理状态聚合为版本化结构化快照。

门禁：

- 快照只读投影，不成为新的事实源；
- 文档渲染只消费快照；
- 快照绑定目标字段、Mapping、证据、血缘版本和语义版本；
- 旧 Markdown/Excel 导出结果保持兼容；
- AI 草稿不能覆盖人工最终内容。

### Phase 13：真实覆盖率和业务看板

目标：展示语义覆盖、Mapping 覆盖、血缘覆盖、待确认问题、冲突和影响风险。

门禁：

- 分母、分子和排除项可追溯；
- 空分母返回 `null` 或“暂无可计算对象”，不能显示为 0%；
- 只统计 confirmed/approved/verified 事实；
- AI suggestion 不计入正式覆盖率。

### Phase 14：数据质量期望

目标：把 not-null、唯一性、枚举、范围、引用完整性、时间一致性和自定义表达式绑定到语义和目标字段。

门禁：

- 质量规则有治理状态和证据；
- 可以被需求、Mapping 和 UAT 复用；
- 不把质量建议误报成已经执行过的质量结果。

### Phase 15：语义影响分析

目标：把现有 SQL 变更影响沿 `LineageNode/Edge`、`SemanticBinding` 和需求快照继续传播。

门禁：

- 影响结果包含路径、证据、版本、置信度和待确认状态；
- 能进入现有 ReviewTask/Workflow；
- 不复制技术血缘模型。

### Phase 16：Canonical Lineage Revision

目标：增加项目级血缘版本、按版本查询和图 Diff。

门禁：

- v1 和 v2 图可以独立读取；
- 旧版本不会被新脚本覆盖；
- 脚本格式化变化不会造成伪语义变化；
- 字段、Join、Filter、转换和删除均有结构化差异；
- 需求快照能引用血缘版本。

### Phase 17：端到端路径和脚本监控

目标：打通 Source → 数仓 → 监管集市 → 一表通/EAST/1104，并支持定时同步、变更告警和审核闭环。

门禁：

- 至少一条黄金链路完整可追溯；
- 脚本删除、解析失败、字段重命名和 Join 变化均有明确状态；
- 高风险变化能够生成影响分析和审核任务；
- 不执行上传脚本。

### Phase 18：数据星云和业务化展示

目标：完成星云总览、分层 DAG、版本时间线、影响聚焦和业务名称优先展示。

门禁：

- 图和表格显示相同事实；
- 业务名、技术名、证据和版本可以相互跳转；
- 大图有限深、有限节点、渐进加载；
- 有键盘访问、降动画和空态/错误态；
- 不把动画当成运行事实。

## 10. 必须准备的测试夹具

不要只写单元测试，必须建立可重复的黄金夹具：

### 10.1 一条完整链路

```text
源系统客户表
→ ODS 客户表
→ DWD 客户明细
→ 监管集市客户表
→ 一表通目标表
→ EAST/1104 输出字段
```

每层至少包含：

- 中文备注；
- 技术字段名；
- 主键或业务关联键；
- 统计日期；
- 一条真实 Join；
- 一条 Filter；
- 一个码值转换。

### 10.2 至少五种脚本变化

1. 只改注释；
2. 新增来源字段；
3. 删除来源字段；
4. 修改 Join 条件；
5. 修改 Filter 或聚合规则；
6. 字段重命名；
7. 文件删除；
8. SQL 无法解析。

### 10.3 需求缺口夹具

至少覆盖：

- 能直接找到字段；
- 需要跨表 Join；
- 没有可用关联键；
- 缺少时间字段；
- 需要字典表；
- 一个业务字段对应多个技术字段；
- 中文备注缺失或冲突。

## 11. 验收标准

### 功能验收

- 可以从一个监管字段看到 Source → 数仓 → 监管集市 → 一表通/EAST/1104 的完整路径；
- 可以切换历史血缘版本；
- 可以看到字段新增、删除、重命名、Join、Filter、聚合和转换差异；
- 脚本变化可以定位到下游中文业务字段和需求文档；
- 需求文档精确到表、字段、关联条件和取数规则；
- 当前数据不足时生成有证据的字段/表/桥接表/字典表建议；
- 页面默认使用中文业务名称；
- 技术名称仍可查看和导出；
- 高风险变化进入人工审核；
- 解析失败不覆盖上一版正式血缘。

### 安全验收

- 所有请求检查 project 和 institution scope；
- 受限实体只返回类型占位符；
- Git 凭据只从环境变量注入；
- 不执行用户上传的 SQL、Shell、Git hooks 或仓库程序；
- 模型只接收允许外发的元数据和脱敏证据；
- 审计日志记录同步、解析、绑定、发布、审核和导出；
- 没有真实密钥、Token、密码进入代码、数据库 payload 或错误日志。

### 回归验收

至少运行：

```text
cd backend && python -m pytest -q
cd frontend && npm run build
cd backend && python -m alembic upgrade head
python scripts/smoke_test.py
```

需要重点回归：

- `backend/tests/test_sql_lineage.py`；
- 语义目录和语义安全测试；
- 双层 Mapping 测试；
- 需求工作台投影测试；
- Deliverable/Excel/Markdown 导出测试；
- 权限、审计和数据隔离测试；
- 前端字段工作台和语义目录测试。

## 12. Codex 执行规则

### 12.1 开始前必须做的事

1. 读取根目录和相关目录的 `AGENTS.md`、`README.md`、`.planning/PROJECT.md`、`.planning/REQUIREMENTS.md` 和当前阶段文档。
2. 检查 `git status`，保留现有未提交修改，不执行 reset、checkout、clean 或覆盖式复制。
3. 盘点现有模型、迁移、API、服务、前端路由和测试。
4. 创建基线报告：
   - `docs/upgrade/00-baseline.md`
   - `docs/upgrade/01-gap-analysis.md`
   - `docs/upgrade/02-adr-index.md`
5. 将本文需求映射到已有模型和待新增模型，先说明复用关系。
6. 如果发现当前工作区存在与本任务冲突的未提交修改，先记录冲突并停止写入冲突文件。

### 12.2 代码实施规则

- 优先增量迁移和兼容 API；
- 优先模块化单体，不无理由拆微服务；
- 不重复创建 Metadata、Lineage、Knowledge、Governance 模型；
- 不先做视觉，再倒推数据；
- 不把 AI 推断写入 confirmed/final 字段；
- 不把渲染后的 Word/Excel/Markdown 当作事实源；
- 不用字符串拼接代替实体关系校验；
- 不用图形库内存状态代替数据库版本事实；
- 所有新增写操作都有权限、幂等、审计和回滚边界；
- 所有异步任务都有可恢复状态和失败原因；
- 迁移必须同时覆盖 PostgreSQL 和 SQLite；
- 新接口必须有 schema、权限测试和错误码；
- 新前端页面必须覆盖 loading、empty、error、unauthorized、truncated 和 reduced-motion 状态。

### 12.3 子代理规则

子代理默认继承父线程当前选定的模型型号和推理强度。委派时默认不传 `model` 或 `reasoning_effort`；只有用户、任务或角色契约明确要求时才覆盖。角色名表示工作职责，不代表默认模型品牌。

子任务必须写明：

- 目标；
- 可读取和可修改的文件范围；
- 禁止事项；
- 验收标准；
- 要返回的证据。

不得让两个写代理修改同一个文件或同一条紧密耦合链路。父线程必须审查代理结果，不能把代理结论直接当成事实。

### 12.4 停止条件

遇到以下情况必须停止当前阶段并报告，而不是自行猜测：

- 无法确定现有字段或模型的权威来源；
- 需要删除或重命名现有 API/模型；
- 需要把历史事实覆盖为新解析结果；
- 需要访问生产数据库或执行生产脚本；
- 需要真实凭据、生产样本或未脱敏敏感数据；
- 当前数据库迁移无法同时保证 PostgreSQL/SQLite；
- 解析器无法区分技术事实和 AI 建议；
- 当前工作区的未提交修改与目标文件冲突；
- 图规模超出当前查询预算但没有性能方案。

## 14. 版本判断

这不是一次普通页面迭代，原因是它会改变：

- 血缘事实的时间和版本模型；
- 需求文档的结构化输出契约；
- 影响分析的传播范围；
- 前端的主要工作方式；
- 字段名称的展示契约；
- 数据库迁移和 API 兼容策略。

因此产品管理上应按重大版本规划，工程实施上必须按 Phase 12—18 的增量阶段推进，不得采用“大爆炸式重写”。
