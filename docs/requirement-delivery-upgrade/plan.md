# 需求交付升级计划（plan）

## 1. 目标与边界

本轮目标是把「跑批 SQL → 可追溯需求文档」从"演示级"推到"可控交付级"，六个方向：

1. 减少解析静默损失（P0-C）
2. 补齐"引用合法但正文语义错误"的候选质控（P0-B）
3. 支持经适配验收的客户 DOCX / XLSX 需求模板（P0-D / P1-B）
4. 冻结正式导出产物可重放（P1-A）
5. 建立真实业务准确率与人工、规模成本的可测量机制（P0-A / P1-C）
6. 在保留治理链前提下完善检索、运行事实、外部集成与容量恢复（P1-D / P2-A~C）

不可让步的约束（任何改动都不得削弱）：证据可追溯；候选必须人工采纳；业务/技术/终审三级审批；冻结快照与完整性校验；历史正式交付不可覆盖；项目/机构/权限/保密边界。

明确禁止：减少审核环节、自动关闭缺口、放宽既有校验、让模型直接写正式正文。

## 4. 依赖与顺序（为什么这样排）

1. **先做 P0-C**：解析静默丢值是"上游失真"，后续任何准确率指标都会被它污染；不先修，测出来的准确率没有解释力。
2. **P0-B 紧随其后**：解析可信之后，才有意义去校验"候选正文是否被固定事实支持"。
3. **P0-D / P1-B 在 P0-B 之后**：模板渲染只消费冻结 JSON，冻结内容是否可信取决于前两项。
4. **P1-A 应在 P0-D/P1-B 之后**：产物落库要先有稳定的渲染身份（模板 hash / 映射 hash / 渲染器版本），否则存下来的产物无法判定为"同一身份"。
5. **P0-A 需要真实案例与独立标注人**，不依赖代码顺序，但依赖用户提供资料；本轮不虚构。
6. **P1-C / P1-D / P2-* 依赖真实环境**（真实 PG/Redis/Milvus、真实 provider、真实客户运行事实），本轮无授权环境，不臆造结论。

## 5. 本轮刻意不做的事

- 不做"任意客户模板自动理解引擎"：客户模板必须先完成适配配置（锚点 / 命名单元格 / 样板行），未经适配的模板一律失败，不猜。
- 不把公式计算结果交给模型"推断"：只报告"缺失 + 定位 + 处理建议"。
- 不把 `check_candidate_compliance` 变成"模型裁判"：语义校验只做确定性事实匹配，判定不了的写 unknown 并阻断，不静默放行。
- 不改历史冻结 JSON、不重算历史 hash、不批量把旧候选标为已验证。

### 7.20 导出前字段级差异（round 19）

- 差异只比字段口径四段（业务定义/业务正文/技术加工/技术正文），空白与 `null` 归一，**不比格式**；新增字段与删除字段分别计数。

- 边界：只与**最近一次**快照比；不比较资料范围/缺口/脚本依据的逐项内容（只体现在"会新建快照"这一句上）；快照内容的读取依赖产物完整性校验，快照 JSON 本身损坏时报错而非静默空。

### 7.21 冻结状态常驻可见（round 20）

- 问题：冻结状态只在"点导出"时才出现（round 18/19 的预检弹层）；用户改完口径后，工作台常驻区域看不出"当前内容是否已经冻结"。快照列表也只有"需求 vN · 时间"，没有任何"哪份是最新、哪份落后于当前内容"的标记，`is_latest` 甚至没有从服务端返回。
- 服务端：`GET …/snapshots` 的每一项新增 `is_latest`（由服务端在 `order_by(id desc)` 结果上判定，界面不能自己按时间猜）。
- 界面（`RequirementSnapshotsPanel.tsx`）：新增 `aria-label="冻结状态"` 区块，三态：无快照 / 已冻结在快照 #N（内容 hash 一致）/ 最近快照 #N 之后仍有未冻结改动；每条快照加"最近"与"与当前内容一致 | 落后于当前内容"徽标；有未保存编辑时补一句"另有未保存的编辑，保存后才会进入冻结判断"。
- 判据只用 `content_hash`（与导出复用快照、与导出前差异完全同一口径）；禁止按 `requirement.version` 推断。
- 真实浏览器两态：`当前内容已冻结在快照 #18（内容 hash 一致），再次导出会复用该快照。`；真实编辑后 `最近快照 #18 之后仍有未冻结改动（内容 hash 已变化），下次导出会新建快照。`
- 边界：只反映"内容是否与最近快照一致"，不判断"内容是否已达可交付"；快照数量上限仍为列表 200 条；未做 100+ 快照的渲染测量。

### 7.22 任选两份快照对比（round 21）

- 不适用：内置版式 xlsx 与客户模板 docx 没有可自检的表级结构 → 明确"不适用"（422 / 批量跳过），
  不算通过、不算失败、不写记录；可自动验收的为 0 时按钮消失并提示"需要人工核对后另行登记"。
- 诚实性：批量不改变交付状态、不关缺口；通过只代表文件本身对得上（real-run-20261024.md §70）。
### 7.68 round 66：人工核对登记（不适用自动验收的产物也要有人负责）

- 入口：交付审计表格里，仅对 `acceptance_applicable === false` 的行出现「登记人工核对」按钮 → `POST …/render-artifacts/{id}/attestations`。
- 两种结论：人工核对通过 / 不通过；依据少于 4 字或占位词（"已看""详见附件"）被拒。
- 口径：登记不写检查记录、不加 `checked` 计数，审计另列"其中 N 个已有人工核对登记（不通过 M 个）"。
- 修复：`auditReload` 进 effect 依赖，登记成功后审计卡就地刷新（此前界面停在旧快照）。
- 边界：人工登记 ≠ 业务口径确认 ≠ 已检查；不关缺口、不改交付状态。

### 7.69 round 67：人工核对结论进入交付就绪度

上一轮把"不适用自动验收的产物"接上了人工登记，但登记结论不影响任何判定——看板照旧写
"可直接重新导出"。本轮把 `rejected` 接进就绪度：

- 就绪度 `requirement-delivery-status-v6`，`human_rejected` 为最高优先级，但**只压登记的那一版产物**；
- 看板筛选/排序/详情/登记摘要四处同步，`READINESS_RANK.human_rejected = -1`；
- 真实环境验证：产物 `#66` 登记不通过 → `readiness=human_rejected`、`summary 0→1`、审计 `checked` 不变；
- 浏览器验证：筛选 `人工核对不通过 1` 命中、详情明确写出被判原因、控制台 0 错误。

不在本轮范围：把"不通过"转成待办派工（下一轮候选）、通知责任人。

### 7.70 被否产物的下家（round 68）

上一轮「人工核对不通过」只压住就绪度，缺"谁去做、做什么"。本轮把被否文档按字段展开进派工清单：

- 原因 `artifact_rejected` 排在四类之后（补正文/补映射仍优先），字段行带产物号、判定时间、依据原文；
- 清单顶部单列被否文档（需求/监管表/产物/影响字段数/未关闭缺口数）；
- 判定只认最新产物上的最新登记，旧登记保留但不影响当前文档；
- 顺手修掉"UTC 当本地时间"的显示缺陷（`formatServerTime()`）。

不做：不自动建待办行、不自动改就绪度以外的状态、不阻止再次导出。

### 7.71 被否之后：换版式不算改（round 69）
上一轮把被否产物接进了派工清单，但判"是否仍被否"看的是**产物 id**，于是"换版式重导一次"就能让红牌消失。
本轮把这个口子堵上，并让"被否之后发生了什么"可读：

- 判据改内容哈希（`requirement-delivery-status-v7`）：只要最新产物的 `content_hash` 与被否那份相同，红牌继续压着；
- 新增被否跟进三态（`requirement-rejection-followup-v1`）：仍被否 / 重导但内容没变 / 重导且内容有变化，
  经 `GET /projects/{project_id}/rejection-followup` 与派工清单同时暴露；
- 派工清单里被否字段的解除条件同步改成"内容变了"（`requirement-field-worklist-v3`）；
- 界面在「被否产物提示」下方多一块「被否后续核对」，写明"内容变了不代表已通过，换版式更不代表改动"。

不做：不自动把重导当通过、不关缺口、不提交通知；不做"人工复核通过"的二次审批流。
### 7.72 字段覆盖核对（round 70）

**动机**：导出文档只渲染需求范围内的字段，漏掉的字段在文档里没有任何痕迹；评审无法从文档看出"模板要填的字段少了哪几个"。

**做法**：只读端点 + 看板弹层，把差集按证据强弱分三类（集市映射 / 脚本血缘 / 都没有），并给出每类"为什么值得关心"的说明；明令不自动补字段。

**验收**：真实 21 条需求汇总（237/231/6）、真实浏览器弹层三段齐全且无"一键补齐"入口、后端 5 用例与前端 3 条契约通过。

**后续**：`mapped` 类未覆盖字段应当能一键转成待办（现在只是"看见"），补字段需要人工确认的受控入口。
### 7.73 交付稳定性核对（round 71）

**动机**：用户要的是"稳定输出"，而既有的 `file_sha256` 只证明第一份文件没被改；冻结导出复用产物，重复导出同字节也不等于渲染可复现。

**做法**：只读重放——取产物的冻结内容，用当前代码同一渲染器重渲，比 sha256；判定顺序为 产物完整性 → 渲染器版本 → 冻结内容 → 字节。

**关键取舍**：旧版渲染器产物记 `historical` 而不是 `renderer_drift`。用新代码重放旧产物比出来的差异不是缺陷，混进告警会让核对失去可信度。

**验收**：真实 47 个产物 `identical 11 / drift 0 / historical 35 / unsupported 1`；后端 6 用例覆盖四类结论；真实浏览器计数与接口一致。
### 7.74 交付审计的复核维度（round 72）

**动机**：round 71 的重放核对是独立入口；交付审计只看"查没查过"，看不见"查不了的那些"。旧版渲染器产物在列表里与普通产物无异。

**做法**：审计逐项给 `replay` 三态（只读元数据，不重放，避免列表页退化成全表重渲），卡片加一行风险提示，行内加标；`checked` 口径不动。

**验收**：真实 47 个产物 → 11 / 35 / 1，与重放核对一致；后端 4 用例、前端 4 条契约、真实浏览器 10 项断言全过。
### 7.75 交付复核清单（round 73）

**动机**：round 72 的复核维度只出现在审计行里，看不到全量与分布；"某张表的历史产物还能复核吗"只能翻列表。

**做法**：新增只读清单端点与弹层，支持状态/渲染器/需求/关键字筛选，facets 用全量算；三态判定复用交付审计的 `replay_kind` + `current_renderer_version`。

**验收**：真实 47 个产物 → 11 / 35 / 1，与重放核对、交付审计三方一致；后端 5 用例、前端 5 条契约、真实浏览器 11 项断言。

**交接**：暂停开发，改动冻结到 `dsh/handoff-20261025-round73`；后续计划见 `handoff-20261025.md` 第 6 节。
