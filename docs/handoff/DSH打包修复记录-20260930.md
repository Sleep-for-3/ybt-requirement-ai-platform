旧包 `ai-platform-dsh-20260930-122934.zip` 不再用于环境复现。它的 1137 文件清单通过自身哈希校验，但打包脚本曾错误排除所有名为 `storage` 的目录，导致 `backend/app/services/storage/` 的五个 Python 源文件缺失。`backend/app/main.py` 导入该包后失败，M0 无法完成；这是打包规则缺陷，不是目标电脑通过安装依赖就能解决的问题。

目标电脑操作：暂停 M0 后续工作；用新完整 ZIP 在独立目录解压，将其作为新的交接基线；核对包内五个文件和 manifest 后重新运行 M0。不要直接在旧 ZIP 中添加文件却仍宣称旧 1137 文件哈希清单完整。旧工作目录若已有 dsh 的 M0 报告或其他新产出，先保留报告并明确“原交接包缺失源码”，不要用解压覆盖正在修改的业务代码。

新包的源文件哈希、ZIP CRC、必需文件和排除路径检查结果见同目录生成的 `.verification.json`。该校验仅针对文件完整性与路径，不代替目标机依赖安装、导入及测试，也不构成源码/业务资料的内容级脱敏审计。

再次复查后，打包脚本已升级为遍历当前项目树、仅排除明确的运行产物和旧重复发行副本。打包前强制核对当前 Git 跟踪文件是否遗漏，并静态解析后端 app 中的绝对 `app.*` 导入，确保对应 Python 模块也被选中。与早期 1143 文件的局部修复包相比，后续“完整重打包”包含更多当前项目文档、规划资料和相关源码；只使用最后生成的完整包。静态导入检查无法证明目标机依赖已安装，也无法覆盖运行时动态导入，因此 M0 仍须在目标机运行。
