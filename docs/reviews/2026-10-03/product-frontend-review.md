## 3. 源码可以定位的 Bug

严重度约定：P1 必须在业务试点验收前修复；P2 必须纳入近期产品版本。以下为源码逻辑确认，未宣称浏览器实测复现。

### PF-01 / P1：四类表单服务端成功后，前端报错或不刷新

- 位置：`app/model-profiles/page.tsx:119-122`；`app/admin/users/page.tsx:53-61`；`app/admin/institutions/page.tsx:50-55`；`app/mart/page.tsx:37-44`。
- 触发：创建/修改请求成功返回后，执行 `event.currentTarget.reset()`。
- 根因：异步函数 `await` 后重新读取 React 事件 `currentTarget`；React 派发结束后会清空它。当前安装的 React 源码 `node_modules/react-dom/cjs/react-dom.development.js:9042` 也可验证该事件行为。
- 影响：后端已经创建用户、机构、集市表或更新模型，前端却进入 catch 或跳过后续列表刷新；用户可能再次提交，造成重复数据/重复用户名报错。
- 修复与验收：在首个 await 前捕获表单元素；隔离接口返回成功时，四类表单均正确关闭/清空/刷新且没有错误提示，接口失败时保留填写内容。测试必须核对实际请求次数与服务端结果。

### PF-02 / P1：只修改模型档案名称也会重置经过调优的调用参数

- 位置：`app/model-profiles/page.tsx:109-116`；`backend/app/api/ai_runtime.py:280-286`。
- 触发：已有档案使用非默认 output token/temperature/timeout/retry/json_mode 参数，用户只在编辑表单改名称后保存。
- 根因：前端固定发送 `json_mode=true, max_output_tokens=2048, temperature=.2, timeout_seconds=60, retry_count=2`；后端将整个 config_json 替换。该表单没有展示这些原配置供用户确认，同时 `last_connection_test` 会被默认值清空。
- 影响：提示词对应的模型行为、耗时和可输出长度发生意外改变；“改名”成为运行参数变更。
- 修复与验收：编辑必须保留未修改参数或提供完整参数表单和变更预览。以非默认档案只改名，逐项比较修改前后的完整 JSON，除明确选择修改的字段外必须相同；配置变更按现有 Skill 依赖门禁复验。

### PF-03 / P1：切换项目或切换需求时可直接丢失未保存的字段/Skill编辑

- 位置：`components/ProjectContext.tsx:71-79`；`components/AppShell.tsx:309-313`；`RequirementScopePanel.tsx:27`；`RequirementWorkspace.tsx:177-200,303`；`DocumentPreview.tsx:146-148`。
- 触发 A：在需求字段正文或 Skill 提示词中输入未保存文本，再使用顶栏项目选择器。项目会立即变化，带 key 的项目边界卸载页面。
- 触发 B：需求 A 的字段正文未保存、需求说明本身没有修改，使用“选择需求”切到 B。choose() 只检查需求说明自己的 dirty，不检查字段 editorDirty，旧编辑器被卸载。
- 影响：人工工作丢失；局部表/场景/字段切换确认并不能覆盖这两个入口。Skill 的 beforeunload 也不能覆盖应用内部的项目选择。
- 修复与验收：建立页级未保存编辑登记与统一导航守卫，包含正文、范围、Skill、制度人工对照等表单。分别测试项目、需求、字段、场景、路由、浏览器关闭；取消切换保持内容和上下文，选择放弃才切换；保存进行中必须给出确定结果。

### PF-04 / P1：有未保存正文时，仍可应用 AI 采用清单并切换版本

- 位置：`RequirementGenerationPanel.tsx:91-96,121`；`RequirementWorkspace.tsx:309-311`；`RequirementContentEditor.tsx:40,48,70`。
- 触发：先把候选加入采用清单，接着在主编辑器修改正文但不保存，再点击“应用采用清单”。
- 根因：generate() 检查 dirty，但 adoptBasket() 及按钮只检查 busy；采用成功回调将父级 editorDirty 清成 false。编辑器内部仍可能保存旧基准的输入，而新 contentVersion 已传入。
- 影响：未保存编辑与新候选版本混合；父级保护状态与编辑器状态不一致。后续导航可能丢稿，或按新的预期版本保存基于旧内容的全部字段。后端版本保护不能替代前端未保存输入的保护。
- 修复与验收：dirty 时禁止加入/应用清单或要求先保存并重新校验候选；采用前后保持明确的版本基准。验收应断言 dirty=true 时无 adopt 请求，保存新版本后旧候选明确过期，采用成功不会偷偷清除其他表单的 dirty。

### PF-05 / P2：同版本多轮生成与历史候选缺少正常访问入口

- 位置：`RequirementGenerationPanel.tsx:51,61,118-121`；`backend/app/api/requirements.py:354-367`。
- 触发：内容 v1 先生成整表、再只生成当前字段。后台按 input_id 倒序返回，currentRun 仅取第一轮，前一轮其他字段候选不再显示。修订到 v2 后，所有 v1 轮次都被 stale 过滤。
- 影响：已花费模型资源产生的候选难以逐项审核，失败原因和拒绝/采用历史缺少业务入口；页面内“历史候选只读”的文案没有完整的正常进入路径。
- 修复与验收：加入按内容版本/生成轮次切换、全量候选状态列表与失败详情；历史只能查看/拒绝、当前采用仍受版本/hash保护。两轮生成后前轮候选必须可见；版本升级后旧输入、候选、原因和人工决定必须可追溯。

### PF-06 / P2：窄屏收起分析侧栏后无法再展开

- 位置：`RequirementWorkspace.tsx:295-304`。
- 触发：视口低于 lg，在分析范围侧栏点击“收起”。
- 根因：包含“展开”按钮的整个父容器被设为 `hidden lg:block`；没有留在可见区域的恢复入口。
- 影响：用户无法继续选择表、场景、需求或生成范围，只能刷新/放大视口。
- 修复与验收：把折叠控制放到始终可见位置；390px/768px 视口反复收起展开后，按钮可见、原选择保留、焦点可恢复。

### PF-07 / P2：拥有业务权限的 UAT 用户和审计员缺少对应导航

- 位置：`components/AppShell.tsx:86,89`；`lib/navigation-contract.mjs:69-79`；`backend/app/services/auth/permission_service.py:14-23,70`。
- 触发：只具有项目业务分析/技术分析/审核/auditor 角色，没有机构/平台 admin 能力。
- 根因：UAT 与审计入口按 audience=admin 判断；后台已经允许上述角色 uat.view/execute/signoff 或 audit.read。
- 影响：已授权业务操作难以从导航发现，用户依赖直接 URL 或局部深链；正常验收流程被挤进“设置”。这属于入口缺陷，不能据此宣称后端越权。
- 修复与验收：以具体项目权限决定 UAT/审计可见性；分别登录分析、审核、审计、viewer、管理员，导航与允许的操作一致，不要求业务用户获得管理员身份。

### PF-08 / P2：需求流程进度使用共享事实，不能准确表示当前需求是否完成

- 位置：`RequirementWorkspace.tsx:290,397-411`。
- 触发：共享字段存在任意 AI 草稿/最终正文，但当前需求专属内容尚未生成、审核或正式交付；或反过来当前需求已完成，而共享事实不满足该条件。
- 根因：StepBar 的 hasDraft/hasFinal 使用 projection.records.some()，并未读取当前需求版本、候选或审核状态。
- 影响：任意一个共享字段的正文就可能让“人工校核与导出”显示完成；不能代表全量范围通过校核，更不能表示正式交付。
- 修复与验收：对需求模式使用当前范围、内容版本、候选处理数、审核状态及正式版本；共享参考模式明确标注。8 个字段只完成 1 个时，进度不能完成；正式交付必须绑定同一已审核 hash。

### PF-09 / P2：部分接口失败被表现为“没有任务/没有审计记录”

- 位置：`app/agent/page.tsx:99-109,171-197,220-245`；`app/audit/page.tsx:32,60-64`。
- 触发：Agent tools/tasks 请求 403、500 或断网；审计请求失败。
- 根因：Agent tools/tasks 没有独立 error 区域，undefined 被显示为 0 和“还没有任务”；审计 catch 直接 setItems([])，界面显示“暂无审计记录”。
- 影响：运维故障和权限不足被误判为空业务；审计使用者可能得出错误结论。
- 修复与验收：加载中、无权、失败、空数据分别展示；失败保留最后成功状态并标明时间。模拟 403/500/断网时不得显示“暂无记录”作为结论，必须可重试。

## 5. 建议的升级顺序与交付门槛

1. **修复版**：先完成 A 与现有接口/配置兼容核验，再处理 PF-05～09。交付一份缺陷复现与复测记录，不以“构建成功”替代业务回归。
2. **试点验收版**：完成 B/C/D/F；只选一条能由业务专家解释并复核的需求链路，生成→差异采用→制度/路径核验→独立审核→正式文件→UAT，全部使用固定版本。留下匿名化证据包和操作录像/截图。
3. **可规模协作版**：完成 E/G/H/I；在现有已跑通闭环上增加更多场景和资产规模。工程层面的迁移、队列并发、容量、离线部署、备份恢复及监控门禁应使用本轮工程审查报告，不从产品页面数量推断。
