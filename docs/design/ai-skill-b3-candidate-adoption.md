# B3 目录候选进入人工采用流程

日期：2026-09-29。适用于字段场景页的有界目录召回，不代表真实模型语义匹配质量验收。

## 四步流程

1. **加入来源候选**：`POST /ai-skills/field-candidates/prepare` 接收完整原查询、context_hash、候选 ID 和场景 ID。真实用户必须具有本项目 technical.edit 权限；重新召回验证快照和候选白名单，场景必须属于该项目且启用。不接受客户端提供的字段描述、评分或加工逻辑。创建未选择、未探查的推荐记录，不创建或改写 Mapping。
2. **选择候选**：复用现有选择入口；重新授权并核对目录快照，创建/关联技术映射及目录证据，仍不写来源字段。选择不是采用。
3. **安全探查**：沿用独立 profile.request 权限及只读 SQL 执行器。新候选必须通过目录快照检查才可进入实际探查。此步骤是用户主动操作，不由召回或模型自动触发。
4. **人工采用**：服务端检查选中状态、该推荐/项目/字段/场景/数据源/列对应的最新探查任务及统计快照。只接受 completed 或 partially_completed、已结束且具有 total_count 的有效统计；无有效探查不能绕过前端直接采用。新候选再次校验目录版本。采用后技术确认状态仍为 draft，加工规则仍需人工确认。

## 数据与事务

- 复用既有 CandidateSourceRecommendation 和审计表，无数据库迁移；新记录标记 bounded_catalog_recall。
- 目录版本哈希保存于 prepare_field_candidate 审计事件；审计缺失、目录停用、项目/表/Schema 关系变化或内容版本变化均拒绝继续。哈希元数据不是知识引用，不混入 citation_summary_json。
- 在授权后锁定目标字段，再重读目录快照，重复加入相同项目/字段/场景/列版本复用记录。选择、探查和采用是分开的操作，不隐式完成下一步。
- 原有目录推荐也增加服务端有效探查门禁；原有非目录推荐语义保持不变。固定 RequirementRevision 不受影响。

## 权限分类修复

真实技术分析员浏览器验收发现通用资源守卫过早要求业务编辑/目录管理权限。修正场景映射 GET 为项目读取、列探查 POST 为 profile.request；hybrid-search/planned-search 为 knowledge.search。具体写操作和上传管理权限保留。项目经理没有默认 profile.request，本轮未给该角色增权。

## 验证与限制

- 后端 `b3-preparation-final.xml` 58 passed，覆盖准备幂等、白名单/范围/身份、目录变化、探查门禁、权限守卫，以及既有元数据与检索回归。五条 JUnit record_property 格式警告不影响测试结果。
- 前端最终生产构建通过，保留既有 lint warnings。浏览器使用临时 SQLite 合成源库，通过实际安全探查与采用 API；不是伪造成功探查记录，也未连接用户业务库。
- 旧目录推荐没有准备快照审计，不能追溯补成新快照；新候选的固定目录检查仅适用于新流程。PostgreSQL 并发、真实数据源环境及模型质量未验证。
