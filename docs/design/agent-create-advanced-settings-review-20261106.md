# 新建任务「高级设置」评审与执行方案（2026-11-06）

评审对象：`/agent` 新建任务面板红框区域（`frontend/app/agent/business-ui.tsx` L524–539）：
「高级设置（技术选项，一般不用改）」折叠块 + 「创建并执行任务」按钮行。

## 0. 结论（先看这一段）

1. **这个折叠块不应保留为“设置”**：它没有任何可调项，只是平台行为说明；标题暗示“有参数可调”，内容却是内部机制（规划、回退、重试次数），与业务用户心智不符。
2. **“模型思考强度”不应放在新建表单第一层**。业内一致做法是：模型与推理预算由**配置侧**（应用/技能/管理员）决定；业务侧最多给一个**业务语义档位**（如“标准/深度”），且必须先有真实运行时支撑，否则就是假开关。
3. **最近一步（P0，半天）**：删掉折叠块；三条信息压成主按钮下一行承诺（可选「执行说明」气泡）；主按钮回到首屏。模型/推理配置继续留在 `/model-profiles`（AI 运行环境）与 `/ai-control/skills`（技能版本与发布）。
4. **若要满足“快/深”诉求（P1）**：做「核对强度：标准/深度」，深度 = 追加一轮独立复核（流程语义），不是模型名/token；需要后端透传与审计，先补能力再上 UI。

## 1. 红框逐项诊断

| 现有内容 | 问题 | 建议 |
| --- | --- | --- |
| 标题「高级设置（技术选项，一般不用改）」 | 名为设置、实为说明；“一般不用改”暗示有可改项，制造犹豫；点开无收益 | 删除标题和折叠容器 |
| 执行方式：后台规划并执行 | 这是承诺，不是选项 | 合并为主按钮下一行：“提交后在后台执行，可随时查看进度。” |
| 规划失败自动回退固定执行计划 | “规划”“固定执行计划”是内部术语，业务人员无法判断影响 | 业务化：“若自动规划不可用，会按平台标准流程继续，不中断任务。”需要细节放「执行说明」 |
| 失败重试最多 3 次 | 平台策略，用户不可控；写死数字会随配置漂移，反而制造“为什么是 3 次”的疑问 | 改为“失败会自动重试并说明原因”，不展示次数 |
| “以上由平台统一配置，需要调整请联系平台管理员” | 把管理边界暴露给业务用户，且引导到错误对象 | 删除；管理员在配置中心看 |
| 按钮行右侧“只读问答直接给结论；生成交付物的环节会停下来等人工确认” | 内容有价值，但与上方三条语义重复 | 保留一句，作为唯一的执行承诺 |

**量化影响**：折叠块展开时高度 90px，正好位于主按钮上方；1366×768（内容区约 698）下，新建面板展开后主按钮已贴近首屏底部，展开该块后主按钮下移 90px 掉出首屏（本地实测：CTA `top` 686 → 776，视口 639）。

## 2. 业内做法（2026-11 核对）

| 产品/能力 | 做法 | 对本项目的启示 |
| --- | --- | --- |
| OpenAI Responses / Chat `reasoning.effort` | 参数取 `none/minimal/low/medium/high…`，随模型而异；官方建议从 `medium` 起，再用代表性任务测 `minimal/low/high` | 推理档位是**开发者/应用参数**，应由应用按场景与评测决定，不是业务表单字段 |
| Anthropic extended thinking | `budget_tokens` 手工预算已标记 legacy，转向 adaptive thinking | 不要做“思考 token 数”这类输入，供应商正在把“想多久”自动化 |
| Microsoft Copilot Studio | 制作者选择 primary model，另有 deep reasoning 开关（预览）；终端用户只提问 | 模型与深度是 **maker/管理员**配置，业务用户不选模型 |
| Dify / Coze | 模型、推理参数在应用/工作流编排侧配置，终端用户不接触 | 配置面与使用面分离 |
| ChatGPT / Claude 消费端 | 有模型/Thinking 切换，但用户自担成本与结果，且是通用助手 | 企业业务系统通常把这类开关收敛到管理员 |

**共同模式**：配置面（管理员选模型/档位）→ 使用面（业务用户只表达任务）→ 运行面（记录实际使用的模型与档位，可审计）。把模型参数直接摊在业务表单里，是消费级助手的做法，不是银行内网业务系统的做法。

## 3. 本项目现状核验（决定方案可行性）

| 事实 | 位置 | 含义 |
| --- | --- | --- |
| 创建接口已有 `use_llm_planner`、`adaptive`、`max_retries`、`auto_start` | `backend/app/schemas/agent.py:11`、`backend/app/api/agent.py:253` | 技术参数存在，前端未暴露——当前做法是对的 |
| `AgentTask` 无 model / reasoning 字段 | `backend/app/models/entities.py`（`AgentTask`） | 任务级“档位”需要新增存储 |
| 默认取 id 最小的启用 `ModelProfile`；显式传入时才用指定 profile | `backend/app/services/llm/prompt_runtime.py:104` | 运行时支持指定 profile |
| 规划器调用未传 `model_profile_id` | `backend/app/services/agent/planner.py:675` | **目前没有“按任务选模型”的链路** |
| 已有 `/model-profiles`（AI 运行环境）与 `/ai-control/skills`（技能版本、绑定模型、审批发布） | `frontend/app/model-profiles/page.tsx:146`、`frontend/app/ai-control/skills/page.tsx` | 配置面已存在，应复用而不是新建 |
| 配置中心设计已把“模型选择按任务和范围绑定”列为待补能力 | `docs/design/ai-skill-configuration-center-design.md` §3.2 / §4 | 方向一致，属于规划内工作 |

**结论**：现在把“思考强度”放进新建表单，前端能画出来，但后端不会真正改变推理行为——这是典型的“假开关”，比不做更伤信任。

## 4. 推荐信息架构

### 业务面（新建任务）

```
[场景卡：查口径 / 制度比对 / 影响分析 / 报告草稿]
业务目标 [textarea]
[P1 可选] 核对强度： (•) 标准   ( ) 深度   深度会多一轮交叉核对，约多 1 分钟
[创建并执行任务]   提交后在后台执行；失败会自动重试并说明原因。
                   （可选）执行说明 ⓘ
```

- “执行说明”气泡内容（业务语言，最多 3 条）：后台执行、可回退不中断、失败重试并给原因。
- 档位只对需要深推理的场景出现（影响分析、制度比对、报告草稿），默认“标准”，不出现模型名/token/温度。
- 若运行时暂不支持档位，则**不显示档位**，只保留一句执行承诺。

### 配置面（管理员 / 项目负责人）

- 平台管理员：`/model-profiles` 配连接与模型；`/ai-control/skills` 按场景绑定模型与推理档位，走版本、测试、审批、发布、回滚。
- 项目负责人：只看“本项目各场景当前使用的模型/档位”，不可改技术参数（避免项目级随意漂移）。

### 运行与审计面

- 任务快照/技术诊断显示：`quality_profile`、实际 `model_profile`、配置来源（平台默认/项目覆盖）。
- `ModelCallLog` 记录 skill 版本、profile、档位，便于复核“同一任务为什么这次更慢/更准”。

## 5. 分阶段执行计划

### P0（0.5–1 天，纯前端，建议立即做）

| 项 | 内容 |
| --- | --- |
| 改动 | `business-ui.tsx` L524–539：删除 `<details>` 高级设置；主按钮下保留一行承诺；如需细节，改为「执行说明」按钮 + 轻量弹层（或链接到详情页帮助） |
| 文案 | “提交后在后台执行，可随时查看进度；失败会自动重试并说明原因。” |
| 验收 | 1366×768 首屏内可见主按钮；默认视图无“高级设置/回退/重试 3 次/联系平台管理员”；新建面板高度减少约 90px；3 人可用性走查无“我该调什么”疑问 |
| 回滚 | 还原 `business-ui.tsx` 单文件 |

### P1（3–5 天，需业务确认是否要做）

前置：先补运行时链路，再上 UI。

1. `AgentTaskCreate` 增 `quality_profile: "standard" | "deep" = "standard"`（枚举，`extra="forbid"` 保持）。
2. `AgentTask` 存 `quality_profile`（或写入 `model_metadata_json` 并建索引字段），快照回显。
3. 运行时透传：`create_task` → planner / 需要模型结论的工具 → `execute_runtime_chat(..., model_profile_id=...)`；由配置决定“深度”对应的 profile 或 reasoning 参数。
4. 前端档位控件（仅三类场景），默认标准；提交参数；详情/诊断显示档位。
5. 测试：参数校验、默认值、老任务兼容、快照回显、权限（可创建者均可用）；对比标准/深度的耗时与复核通过率。
6. 若生产只有单一 `LLM_MODEL`、无法真正改变推理：**暂缓 P1**，改为“深度核对”流程（同模型二次独立核对），这是可交付的真实能力。

### P2（1–2 周，治理）

- 接入 AI Skill 配置中心：`ModelProfile.config_json` 增 `reasoning_effort` / `adaptive` 等供应商无关字段；按 `scenario_key`/`skill_key` 绑定；版本不可变、审批、回滚、项目级覆盖。
- 管理端可视化“场景 → 模型/档位”，任务诊断显示来源；`ModelCallLog` 全量记录。
- 指标：深度档位使用率、P95 时延、单任务成本、人工复核驳回率。

## 6. 不建议做

- 不暴露模型名、`temperature`、`top_p`、`max_tokens`、思考 token 预算、重试次数、是否使用 LLM 规划。
- 不做“高级设置”这类空容器；不用“一般不用改”这类暗示性文案。
- 不让项目负责人在业务页面改技术参数；配置变更必须走配置中心与审计。

## 7. 待确认

1. 业务是否真的需要“快/深”选择？集中在哪些场景？
2. 可接受的时延与成本增量是多少（例如 +1 分钟、+30% token）？
3. 生产模型是否支持可调的推理档位（当前 `.env` 为单一 `LLM_MODEL`）？
4. 档位由谁改：平台管理员统一，还是允许项目负责人覆盖？
